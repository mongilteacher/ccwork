# Create PR — 초안 승인 → E2E 게이트 → PR 생성

브랜치 작업을 마친 개발자가 "PR 만들어줘"라고 말했을 때, **승인 없이 올라가는 PR**과 **깨진 채 올라가는 PR**을 둘 다 막는 것이 이 스킬의 목적이다.

순서는 고정이다: **초안 → 승인 → E2E → push → PR**. E2E가 승인 *뒤*에 오는 이유는, 개발자가 무엇을 올릴지 확정하기 전에 몇 분짜리 브라우저 테스트를 돌리는 게 낭비이기 때문이다. 반대로 E2E가 push *앞*에 오는 이유는, 실패한 브랜치가 원격에 올라가면 되돌리는 비용이 훨씬 크기 때문이다.

## 절대 규칙

- ❌ **E2E가 빨간불이면 push도 PR 생성도 하지 않는다.** 재시도로 넘어가지도, "일단 draft PR로 올려두자"고 제안하지도 않는다.
- ❌ **E2E를 통과시키려고 `e2e/`를 수정하지 않는다.** E2E 실패는 "사용자 여정이 실제로 깨졌다"는 신호다. 기대값을 낮추면 신호만 지워지고 버그는 남는다.
- ⛔ 승인 게이트(2단계)에서 **반드시 멈춘다.** 개발자가 "그대로 진행" 이라고 답하기 전에는 다음 단계로 가지 않는다.

---

## 1단계 — 변경사항 요약과 PR 초안

### 먼저 상태를 확인한다

```bash
git status --short
git branch --show-current
git log --oneline main..HEAD          # 이 브랜치가 쌓은 커밋
git diff main...HEAD --stat           # 파일 단위 변경 규모
```

- **커밋되지 않은 변경이 있으면 여기서 멈추고 물어본다.** push되는 건 커밋된 것뿐이라, 작업 중인 파일이 남아 있으면 PR에 빠진다. 커밋할지, 놔두고 진행할지 개발자가 정한다.
- 커밋이 하나도 없으면 PR을 만들 게 없다. 그대로 알리고 종료한다.
- 이 프로젝트에는 `origin`(본인 저장소)과 `upstream`(원본) 두 리모트가 있다. **PR은 항상 `origin` 저장소 안에서 연다** — 5단계의 `--repo` 참조.

### base 브랜치를 정한다

CLAUDE.md의 TDD 이슈 사이클은 `PR --base feature/<spec>` → squash merge를 따른다. 즉 **base는 main이 아닌 경우가 많다.**

- 브랜치 이름이 이슈 작업(`feat/...`, `issue-N-...`)이고 `feature/<spec>` 브랜치가 존재하면 → base는 그 feature 브랜치.
- 브랜치 자체가 `feature/<spec>`이면 → base는 `main`.
- 애매하면 추론한 값을 **초안에 명시하고 승인 단계에서 함께 확인받는다.** 잘못된 base는 머지 후에야 드러나므로 여기서 짚는 게 싸다.

### 초안을 쓴다

제목은 커밋과 같은 Conventional Commits 형식(`<type>: <한국어 제목>`)을 쓴다. 커밋 메시지를 그대로 복사하지 말고, **여러 커밋을 관통하는 하나의 의도**로 다시 쓴다 — 리뷰어가 읽는 건 커밋 목록이 아니라 이 한 줄이다.

본문은 아래 틀을 따르되, 해당 없는 섹션은 지운다. 빈 제목만 남기지 않는다.

```markdown
## 요약

<무엇을 왜 바꿨는지 2~4줄. 코드를 읽지 않은 사람이 판단할 수 있게>

## 변경 내용

- <파일/모듈 단위가 아니라 동작 단위로>
- ...

## 테스트

- 단위: <추가/수정한 테스트, 없으면 그렇게>
- E2E: `npm run test:e2e` — 승인 후 실행해 통과 확인

## 관련 이슈

Closes #N
```

- **`Closes #N`은 이슈를 자동으로 닫지 못한다.** GitHub은 PR이 _기본 브랜치(main)로_ 머지될 때만 자동 클로즈한다. 이 프로젝트의 이슈 PR은 base가 `feature/<spec>`이라 머지해도 이슈는 열린 채 남는다. `Closes`는 PR↔이슈 연결 표시로 여전히 쓰되, **머지 후 `gh issue close N --repo mongilteacher/ccwork`가 필요하다는 것을 5단계에서 함께 안내한다.** 안 그러면 "닫혔겠지" 하고 이슈가 계속 쌓인다.

- 전부 **한국어**로 쓴다(프로젝트의 사용자 문구 규약).
- 이슈 번호는 브랜치 이름·커밋 메시지·`docs/features/*/issue-*.md`에서 찾는다. 확신이 없으면 넣지 말고 승인 단계에서 물어본다 — 틀린 `Closes`는 남의 이슈를 닫는다.

## 2단계 — 승인 게이트

초안(제목 / 본문 / base 브랜치 / 커밋 목록)을 보여주고 멈춘다. 이렇게 묻는다:

> 이대로 진행할까요? 수정할 부분이 있으면 알려주세요. 승인하시면 `npm run test:e2e`를 먼저 돌립니다.

수정 요청이 오면 반영하고 **다시 보여준 뒤 다시 승인받는다.** 한 번 승인받았다고 이후 수정본이 자동 승인되는 게 아니다.

## 3단계 — E2E 실행

```bash
npm run test:e2e
```

- **E2E를 돌리기 전에 포트를 확인한다**: `lsof -nP -iTCP:5173 -sTCP:LISTEN; lsof -nP -iTCP:3001 -sTCP:LISTEN`.
  1단계에서 이미 봤더라도 여기서 한 번 더 본다 — 초안 검토와 승인 사이에 사람이 `npm run dev`를 띄울 수 있다.
- Playwright의 `webServer` 설정이 Vite(5173)와 시드 사본 json-server(3001)를 자동으로 띄운다. 따로 `npm run dev`를 켤 필요 없다.
- E2E는 `e2e/fixtures/db.seed.json`의 **사본**을 쓰므로 실제 `db.json`은 오염되지 않는다. 개발자가 걱정하면 이 점을 알려준다.
- 5173/3001 포트를 이미 쓰고 있으면 `reuseExistingServer` 때문에 **개발 중인 서버에 붙어 실제 `db.json`을 건드릴 수 있다.** 사전에 실행 중인 dev 서버가 있으면 내리고 돌리라고 안내한다.
- 시간이 걸리는 작업이다. 도중에 끊고 판단하지 말고 끝까지 기다린다.

## 4단계 — E2E 실패 시: PR을 만들지 않고 안내한다

실패한 스펙 이름과 실패 메시지를 먼저 요약해 보여준 뒤, 아래 절차를 그대로 안내한다. **여기서 스킬은 종료한다** — 대신 고쳐주지 않는다. 어느 계층이 깨졌는지는 코드를 쓴 사람이 가장 빨리 안다.

> **E2E 실패 — PR 생성을 중단했습니다.**
>
> ① **Trace Viewer로 실패 지점 확인**
> `npx playwright show-report`
> ② **어느 레이어에서 깨졌는지 판별** — API / 렌더링 / 로직
> ③ **해당 단위 테스트에 케이스 추가 (Red)** — 그 계층의 테스트가 먼저 실패해야 한다
> ④ **프로덕션 코드 수정 (Green)** → 다시 `/create-pr`
>
> ⚠️ **E2E 코드를 고쳐 통과시키는 것은 금지** — 근본 원인 회피입니다.

덧붙일 실무 정보:

- **trace가 안 보이면**: `playwright.config.ts`가 `trace: 'on-first-retry'`이고 로컬은 `retries: 0`이라 첫 실행에는 trace가 남지 않는다. `npx playwright test --trace on`으로 한 번 더 돌리면 타임라인·DOM 스냅샷·네트워크가 붙는다.
- **② 계층 판별의 단서**:
  | 증상 | 의심 계층 | 갈 곳 |
  | --- | --- | --- |
  | 요청이 안 나갔거나 4xx/5xx, 새로고침 후 데이터 없음 | API | `src/api/notes.ts` + 그 계층 테스트 |
  | 요소가 안 보임·라벨/문구 불일치·비활성 상태 | 렌더링 | `src/components/*` 컴포넌트 테스트 |
  | 값은 저장됐는데 내용이 틀림(정규화·검증·중복 등) | 로직 | `src/domain/*` 단위 테스트 |
- ③이 중요한 이유: E2E만 고치면 같은 버그가 다음에 또 E2E까지 내려와서야 잡힌다. **재발을 막는 건 아래 계층의 테스트**이고, E2E는 배선이 이어져 있다는 확인만 한다.

## 5단계 — E2E 통과 시: push + PR 생성

```bash
git push -u origin <현재-브랜치>
gh pr create \
  --repo mongilteacher/ccwork \
  --base <정해진-base> \
  --head <현재-브랜치> \
  --title "<승인된 제목>" \
  --body "<승인된 본문>"
```

- `--repo`를 명시하는 이유: 이 저장소에는 `upstream` 리모트가 있어서, 생략하면 원본 저장소로 PR이 열릴 수 있다.
- 본문은 파일로 넘기는 게 안전하다(따옴표·백틱·개행 깨짐 방지). 스크래치패드에 `pr-body.md`로 쓰고 `--body-file`을 쓴다.
- push가 거절되면(원격이 앞서 있음) 강제 push하지 말고 개발자에게 알린다. `--force`는 남의 커밋을 지울 수 있다.
- 성공하면 **PR URL을 그대로 출력**한다. squash merge와 이슈 클로즈는 개발자의 몫이며, 이 스킬은 머지하지 않는다.
