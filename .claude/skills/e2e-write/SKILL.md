# E2E Write — PRD 사용자 스토리를 Playwright E2E로

`docs/features/{기능명}/prd.md`의 **사용자 스토리**를 읽어, **실제 브라우저에서 실제 mock API(json-server)를 왕복해야만 증명되는** 사용자 여정만 골라 Playwright E2E 테스트로 옮긴다.

- **입력**: 기능명 `$ARGUMENTS` (예: `/e2e-write tag` → `docs/features/tag/prd.md`)
- **읽을 것**: 해당 PRD의 §2 사용자 스토리 + 인수 조건, 그리고 **기존 단위/컴포넌트 테스트**(`src/**/*.test.*`)
- **산출물**: `e2e/{기능명}.spec.ts` (+ 최초 1회 한정 하네스 스캐폴딩)

## 절대 규칙

- ✅ **`e2e/` 디렉터리와 Playwright 설정 파일만** 생성/수정한다.
- ❌ `src/`의 구현 코드도, 기존 단위/컴포넌트 테스트(`src/**/*.test.*`)도 **절대 건드리지 않는다.** E2E가 통과하지 않으면 그것은 구현 버그이거나 시나리오 설계 문제이지, `src/`를 고칠 신호가 아니다.
- ❌ **단위 테스트가 이미 검증하는 규칙을 E2E로 다시 검증하지 않는다** (아래 「중복 금지」가 이 스킬의 핵심).

---

## 이 스킬의 두 기둥

이 스킬이 존재하는 이유는 단 두 가지 원칙을 지키기 위해서다. 시나리오를 고를 때마다 이 둘로 되돌아온다.

### 기둥 1 — E2E는 "다른 계층이 증명할 수 없는 것"만 증명한다 (중복 금지)

이 프로젝트는 이미 테스트 피라미드의 아래쪽이 두껍다. `docs/features/tag/`처럼 도메인 규칙은 `src/domain/*.test.ts`가 `it.each` 표로 20종 엣지케이스를 밀리초 단위로 검증하고, 훅·컴포넌트는 jsdom에서 검증한다. **E2E가 같은 것을 브라우저로 다시 돌리면 느리고 깨지기 쉬운 중복이 된다.**

E2E의 고유 가치는 **하위 계층이 구조적으로 볼 수 없는 것**이다:

- **실제 네트워크 왕복 + 영속성** — 저장 → json-server 반영 → **새로고침(reload) 후에도 유지**. jsdom + mock context는 이걸 증명할 수 없다.
- **컴포넌트 경계를 가로지르는 여정** — 목록에서 노트 선택 → 편집기에서 태그 추가 → 저장 → 목록으로 → 다시 선택. 단위 테스트는 컴포넌트 하나씩만 본다.
- **취소/실패의 서버 진실** — "취소하면 서버에 안 보낸다"를 **새로고침으로 실제 서버 상태를 확인**해 증명.

그래서 규칙 하나당 E2E는 **대표 케이스 딱 하나**만 왕복시킨다. 정규화 20종 표는 도메인 테스트의 몫이고, E2E는 "정규화가 저장까지 실제로 연결돼 있다"는 배선(wiring)을 대표값 하나로 증명한다.

### 기둥 2 — E2E 베스트 프랙티스를 따른다

사용자가 화면에서 보고 하는 것만 테스트하고, 내부 구현에는 의존하지 않는다. 자세한 패턴은 [`references/playwright-patterns.md`](references/playwright-patterns.md)에 있고, 핵심만:

- **사용자 관점 로케이터**: `getByRole`·`getByText`·`getByPlaceholder`·`getByLabel`. CSS 클래스·`data-testid`·XPath에 의존하지 않는다(테스트 대상은 사용자가 보는 것이지 DOM 구조가 아니다).
- **웹 우선 단언(자동 재시도)**: `await expect(locator).toBeVisible()`. `waitForTimeout` 같은 **임의 대기(sleep) 금지** — 비동기 저장·리렌더를 sleep으로 기다리면 느리거나 깨진다.
- **테스트 독립성**: 각 테스트는 **자기 데이터를 스스로 만든다**. 실행 순서·다른 테스트에 의존하지 않는다. mock 서버가 공유 상태라, 테스트마다 **고유한 노트 제목**(타임스탬프 등)을 써서 자기 노트만 조준한다. **전역 목록 개수(`X개 노트`)를 단언하지 않는다** — 병렬 실행에서 깨진다.
- **한 테스트 = 한 여정**: 이름은 검증하는 사용자 스토리를 그대로 드러낸다.

## 실행 순서

### 0단계 — 하네스 존재 확인 (최초 1회 스캐폴딩)

`playwright.config.ts`가 프로젝트 루트에 있는지 본다.

- **있으면** 1단계로.
- **없으면** [`references/harness-setup.md`](references/harness-setup.md)를 읽고 그대로 스캐폴딩한다. 이 프로젝트는 `API_URL`이 `http://localhost:3001`로 하드코딩돼 있고 json-server가 **실제 `db.json`을 수정**하므로, 하네스는 반드시 **시드 사본을 3001에서 띄워 실제 `db.json`을 건드리지 않게** 만든다. 스캐폴딩 파일 목록·전체 내용·`package.json`/`.gitignore` 수정까지 그 문서에 있다. 스캐폴딩 후 개발자에게 무엇을 추가했는지 보고하고 계속 진행한다.

### 1단계 — PRD 사용자 스토리 읽기

`docs/features/{기능명}/prd.md`의 **§2 사용자 스토리** 표(ID·스토리·인수 조건)를 읽는다. 각 스토리가 E2E 후보다. §4 Out of Scope와 §3 ADR도 훑어 "이번 범위 밖"과 "설계 의도"를 파악한다.

### 2단계 — 스토리별 트리아지 (E2E로 쓸 것 / 버릴 것)

**이 단계가 스킬의 핵심이다.** 스토리를 하나씩 세 갈래로 분류한다. 분류하려면 먼저 **기존 테스트가 무엇을 덮는지** 확인한다:

```bash
# 기존 단위/컴포넌트 테스트가 덮는 범위 파악
ls src/**/*.test.* 2>/dev/null
grep -rn "describe(\|it(" src --include="*.test.ts" --include="*.test.tsx"
```

그다음 각 스토리를 판정한다:

| 판정                        | 기준                                                                                                 | 처리                                                               |
| --------------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| **✅ E2E로 쓴다**           | 실제 서버 왕복·영속성(새로고침)·컴포넌트 횡단 여정이 있어야 증명된다. 하위 계층이 구조적으로 못 본다 | spec에 `test(...)` 하나로 작성                                     |
| **⏭️ 스킵(하위 계층 커버)** | 순수 규칙·단일 컴포넌트 렌더·훅 동작. 이미 `src/**/*.test.*`가 검증한다                              | 작성하지 않는다. 대표 케이스 하나만 ✅ 여정 안에 자연스럽게 녹인다 |
| **⏭️ 스킵(E2E 부적합)**     | 브라우저 자동화로 신뢰성 있게 재현 불가(예: **IME 조합 이벤트**), 또는 인프라가 과함                 | 작성하지 않는다. 이유를 보고에 남긴다                              |

**중복 금지의 실제 적용** — 검증 규칙(중복·길이·개수·정규화 20종)은 도메인/컴포넌트 테스트가 표로 덮는다. E2E에서는 그중 **대표 하나**(예: "중복 태그를 넣으면 인라인 안내가 뜬다")만, 그것도 독립 테스트가 아니라 **저장·영속 여정의 한 스텝으로** 확인한다. 표 전체를 브라우저에서 반복하지 않는다.

**트리아지 결과를 먼저 개발자에게 표로 보고하고 승인받은 뒤** 3단계로 간다. 어떤 스토리를 왜 E2E로 쓰고/버리는지가 이 스킬의 판단 근거이므로, 조용히 결정하지 않는다.

### 3단계 — spec 작성

승인된 ✅ 스토리를 `e2e/{기능명}.spec.ts`에 옮긴다. [`references/playwright-patterns.md`](references/playwright-patterns.md)의 로케이터·단언·독립성 패턴과 주석 달린 예제를 그대로 따른다. 한 스토리 = 한 `test(...)`, 이름은 스토리 의도를 드러낸다(한국어 가능).

여러 스토리가 하나의 자연스러운 여정으로 이어지면(추가 → 저장 → 새로고침 → 확인) 한 `test`에 여러 스토리를 엮어도 된다 — E2E는 화면 단위 검증이 아니라 **여정 단위 검증**이다. 다만 실패 지점이 흐려지지 않게 여정 하나의 의도는 하나로 유지한다.

### 4단계 — 실행 → 초록불 확인

```bash
npm run test:e2e
```

`webServer`가 Vite(5173) + 시드 사본 json-server(3001)를 자동 기동하므로 별도로 `npm run dev`를 띄울 필요 없다. 실패하면 원인을 구분한다:

- **테스트 결함**(로케이터 오타, 잘못된 단언) → `e2e/` 안에서 고친다.
- **구현 버그**(스토리가 실제로 충족 안 됨) → **고치지 말고 보고한다.** `src/`는 이 스킬의 범위 밖이다.
- **하네스 문제**(서버 기동 실패, 포트 충돌) → `harness-setup.md` 재확인.

디버깅이 필요하면 `npm run test:e2e -- --ui`(UI 모드)나 `--headed`를 안내한다.

### 5단계 — 보고

개발자에게 다음을 보고한다:

1. **트리아지 결과표** — 스토리별 ✅/⏭️와 사유(특히 "하위 계층이 이미 덮음"으로 스킵한 것).
2. **작성한 test 목록** — 각각이 증명하는 것(영속성/여정/취소 진실 등).
3. **실행 결과** — 통과/실패, 실패라면 원인 분류.
4. **하네스 변경**(최초 1회라면) — 추가한 파일·수정한 `package.json`/`.gitignore`.

## 다른 기능에 쓸 때

경로의 `tag`는 예시다. `/e2e-write {기능명}` → `docs/features/{기능명}/prd.md`를 읽고 `e2e/{기능명}.spec.ts`로 쓴다. PRD에 §2 사용자 스토리 표가 없으면 개발자에게 알리고, 대신 §성공 기준·인수 조건에서 여정을 추출한다.
