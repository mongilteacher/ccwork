# Feature 기획 워크플로우

하나의 feature를 **"아이디어 → 개발 가능한 이슈 단위"**로 변환하는 파이프라인이다.
근거 문서는 [`docs/features/feature-planning-workflow.md`](../../../docs/features/feature-planning-workflow.md). 이 스킬은 그 내용을 실행 가능한 절차로 담는다.

```
spec-original.md (초기 아이디어)
    ↓ 단계 1 — 요구사항 인터뷰
spec-fixed.md (확정된 요구사항)
    ↓ 단계 2 — PRD 작성 + 기술 결정(ADR)
prd.md (단일 기준 문서)
    ↓ 단계 3 — 이슈 분해
issues.md + GitHub Issues (실행 가능한 작업 단위)
```

산출물은 모두 `docs/features/{name}/` 아래에 둔다. `{name}`은 기능 이름(예: `tag`)이다.

## 이 스킬의 핵심: 승인 게이트에서 멈춘다

각 단계 끝에는 **`[GATE]`**가 있다. 게이트에서는 산출물을 사용자에게 제시하고 **명시적 확정을 받을 때까지 다음 단계로 넘어가지 않는다.**

> 이 게이트들이 없으면 AI가 판단 없이 끝까지 달려버린다. 요구사항이 덜 확정된 채 PRD가 나오고, 안이 선택되지 않은 채 이슈가 쪼개진다. 게이트는 생략 가능한 형식이 아니라 이 워크플로우의 본체다.

한 번에 한 단계씩 진행한다. 사용자가 여러 단계를 한꺼번에 요청해도, 각 게이트에서 멈춰 확인을 받는다.

시작할 때 **어느 단계부터 들어가는지** 먼저 파악한다 — 초기 아이디어만 있으면 단계 1, `spec-fixed.md`가 있으면 단계 2, `prd.md`가 있으면 단계 3이다.

---

## 단계 1: 요구사항 인터뷰

### 목적

초기 기능 정의서의 모호성을 제거하고, 엣지 케이스와 결정 사항을 확정한다.

### 입력

- `docs/features/{name}/spec-original.md` (초기 기능 정의서)
- 코드베이스 (기존 구조·패턴 참조)

### 핵심 활동

**AI가 인터뷰어가 된다.** 정의서를 바탕으로 코드베이스를 탐색하고, 구현 전에 확인이 필요한 것을 사용자에게 **한 번에 하나씩** 질문한다. 각 질문에는 **추천안과 그 이유**를 함께 붙인다 — 사용자가 백지에서 고르지 않고 추천을 검토·수정하게 한다.

아래 8개 영역을 빠짐없이 다룬다:

1. 이 기능의 primary user는 누구인가?
2. 최소 동작 시나리오 3개는? (가장 기본적인 사용 흐름)
3. 데이터 저장 방식 — 기존 구조와의 관계는?
4. 경계 조건 — 최대값, 빈 값, 중복, 동시성은?
5. 에러 처리 — 실패 시 사용자에게 어떻게 표시하는가?
6. 기존 UI 패턴과의 일관성 — 어떤 컴포넌트를 재사용할 수 있는가?
7. 성능 제약 — 허용 응답 시간, 데이터 크기 제한은?
8. 향후 확장 가능성 — 이 결정이 다음 feature에 영향을 주는가?

**Ubiquitous Language(용어 고정):** 인터뷰에서 쓰는 용어를 확정한다. 코드·문서·대화가 같은 단어로 같은 것을 가리키게 하고, `spec-fixed.md`에 **"용어 정의" 섹션**으로 명시한다.

### 산출물

- `docs/features/{name}/spec-fixed.md` — 확정된 요구사항 + 용어 정의

### 승인 게이트

```
[GATE] 사용자가 spec-fixed.md를 읽고 확정할 때까지 대기
```

모호성이 제거되고 용어가 고정됐는지 사용자와 확인한다.

## 단계 2: PRD 작성 + 기술 결정(ADR)

### 목적

요구사항·디자인·기술 결정·범위를 하나의 문서로 통합해, **"이 기능이 궁금하면 여기만 보면 된다"**는 단일 기준점을 만든다.

### 입력

- `docs/features/{name}/spec-fixed.md`
- `docs/features/{name}/design.md` (있으면 참조)
- 코드베이스 (기존 패턴 참조)

### 핵심 활동

**2-1. PRD 뼈대 생성** — 기술 결정 섹션은 처음엔 비워둔다(TODO). 구조는:

- **개요** — 기능의 목적과 범위
- **사용자 스토리** — 사용자 관점의 흐름
- **기술 결정** — 어떤 구조 위에 올릴 것인가 (여기에 ADR)
- **Out of Scope** — 이번에 하지 않을 것
- **용어 정의** — `spec-fixed.md`의 Ubiquitous Language 동기화

**2-2. 아키텍처 3안 제안 & 비교** — 최소 3가지 안을 제안하고, **아래 7가지 고정 기준**으로 비교한다. 기준을 임의로 바꾸지 않는다:

| #   | 기준                 | 설명                                   |
| --- | -------------------- | -------------------------------------- |
| 1   | 데이터 구조          | 어떤 형태로 데이터를 저장/표현하는가   |
| 2   | API 레이어 변경지점  | 기존 API에서 무엇이 바뀌는가           |
| 3   | 상태관리 변경지점    | Context/Store에서 무엇이 추가되는가    |
| 4   | 핵심 동작            | 가장 중요한 동작이 어떻게 구현되는가   |
| 5   | 컴포넌트 구조        | 어떤 컴포넌트가 추가/수정되는가        |
| 6   | 기존 패턴과의 일관성 | 코드베이스의 기존 관습과 얼마나 맞는가 |
| 7   | 테스트 용이성        | 단위 테스트·E2E 테스트 작성이 쉬운가   |

비교를 표로 정리한 뒤, **사용자가 안을 선택한다.** AI가 추천은 하되 대신 결정하지 않는다.

```
[GATE] 사용자가 3안 중 하나를 선택할 때까지 대기
```

**2-3. 선택한 안을 ADR 4요소로 "기술 결정" 섹션에 작성한다.** 4요소를 모두 채운다:

```markdown
### 기술 결정 제목

**Context** — 이 결정이 필요한 맥락. 무엇을 풀고 있는가.
**Decision** — 무엇을 선택했는가.
**Alternatives** — 거부한 안과 **각각의 거부 이유**. (이유 없는 거부 금지)
**Consequences** — 트레이드오프. **장점뿐 아니라 단점도 반드시 명시**한다.
```

`Alternatives`에 이유 없이 "이 안은 안 씀"만 적거나, `Consequences`에 장점만 나열하는 것은 이 형식의 위반이다. 거부에는 근거를, 결정에는 감수할 비용을 남긴다.

**2-4. Out of Scope 작성** — "하지 않을 것"을 구체적으로 나열한다. **명시하지 않으면 AI가 맥락을 확장 해석해 범위 초과 구현을 한다.** 애매하게 두지 말고 항목으로 못 박는다(예: "태그 색상 커스터마이징", "태그 자동 추천", "태그 기반 검색").

```
[GATE] 사용자가 Out of Scope을 읽고 확정할 때까지 대기
```

### 산출물

- `docs/features/{name}/prd.md` — 개요·사용자 스토리·기술 결정(ADR)·Out of Scope·용어 정의

---

## 단계 3: 이슈 분해

### 목적

PRD를 실행 가능한 작업 단위(GitHub Issues)로 변환한다. **각 이슈는 독립적으로 TDD 사이클(Red→Green→Refactor)을 돌릴 수 있어야 한다.**

### 입력

- `docs/features/{name}/prd.md`
- GitHub 프로젝트 보드

### 핵심 활동

**수직 슬라이싱 원칙** — 각 이슈에 이 질문을 던진다:

> "이 이슈만 완료하면 사용자에게 보여줄 수 있는 동작이 있는가?"

- **Yes** → 수직 슬라이스다. 그대로 둔다.
- **No** → 다른 이슈와 합치거나 다시 나눈다.

**수평 슬라이싱(레이어별: API → Context → UI)은 금지한다.** 레이어로 자르면 마지막 이슈까지 끝나야 비로소 동작이 나오고, 이슈 단위로 TDD 사이클을 돌릴 수 없다. 각 슬라이스는 타입·데이터·상태·UI를 얇게 관통해 그 자체로 데모 가능해야 한다.

**이슈 크기** — 반나절~하루 안에 TDD 한 사이클을 끝낼 수 있는 크기. 너무 크면 피드백 루프가 느려지고, 너무 작으면 PR 오버헤드가 이득을 넘는다.

**의존성 순서** — 앞 이슈의 결과가 다음 이슈의 입력이 되도록 배치한다. 역방향 개발(뒤 이슈가 앞 이슈를 되돌리는 것)을 만들지 않는다.

**Acceptance Criteria — Given-When-Then 형식** — 각 이슈에 반드시 AC를 넣는다:

```markdown
## Acceptance Criteria

- [ ] Given [사전 조건], When [행동], Then [기대 결과]
- [ ] Given [사전 조건], When [행동], Then [기대 결과]
```

AC는 다음 단계(`/test-scenarios`)에서 테스트 시나리오의 씨앗이 된다. 구체적으로 쓴다.

```
[GATE] 사용자가 이슈 목록을 읽고 수직 슬라이스·AC 구체성·의존성 순서를 확인할 때까지 대기
```

**GitHub 등록** — 게이트 통과 후, 사용자 동의 하에 등록한다:

```bash
gh issue create --title "이슈 제목" --body "설명 + AC + 의존성"
gh project item-add <PROJECT_NUMBER> --owner <OWNER> --url <ISSUE_URL>
```

### 산출물

- `docs/features/{name}/issues.md`
- GitHub Issues (각 이슈에 AC 포함)
- 프로젝트 칸반 보드 Todo 컬럼에 배치

---

## 승인 게이트 요약

| 지점        | 확인 내용                                         |
| ----------- | ------------------------------------------------- |
| 단계 1 후   | `spec-fixed.md` — 모호성 제거, 용어 확정          |
| 단계 2-2 후 | 3가지 안 비교 — 사용자가 안을 선택함              |
| 단계 2-4 후 | Out of Scope — 범위 확정                          |
| 단계 3 후   | 이슈 목록 — 수직 슬라이스, AC 구체성, 의존성 순서 |

게이트에서 멈추지 않고 끝까지 달리면 이 스킬을 잘못 실행한 것이다.
