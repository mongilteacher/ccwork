# Security Review — 커밋 전 타입·보안 게이트

Refactor까지 끝난 코드를 커밋하기 직전, **타입 오류와 보안 취약점을 수집→분류→(승인 후)선별 수정**한다. 이 단계의 핵심은 "다 고치기"가 아니라 **올바르게 분류하기**다 — 학습용 목(mock) 프로젝트에서 심각도만 보고 전부 고치려 들면 배포도 안 되는 dev 도구를 붙잡고 시간을 태우게 된다. 무엇이 진짜 위험이고 무엇이 노이즈인지 가르는 게 이 스킬의 일이다.

- **입력**: 이슈 번호 `$ARGUMENTS` (예: `/security-review 1`) — 보고 맥락·범위 참고용
- **읽을 것**: `CLAUDE.md`(의도된 패턴 파악), 이번 이슈가 바꾼 `src/` 코드
- **산출물**: 3단계 분류 보고 + 승인된 "즉시 수정 필요" 항목의 수정

## 절대 규칙

- ❌ **판단이 필요한 항목은 개발자 승인 없이 고치지 않는다.** 이 스킬은 스캐너지 자동 수정기가 아니다. 취약점 수정은 의존성 버전을 올리거나 코드를 바꾸는 일이라, 잘못하면 동작을 깨뜨린다.
- ❌ **`npm audit fix --force`를 쓰지 않는다.** `--force`는 semver major를 건너뛰며 올려 **호환성을 깨는 breaking change**를 조용히 들여온다. 방금 초록불 만든 걸 무너뜨리는 지름길이다. 일반 `npm audit fix`(하위호환 범위)만, 그것도 승인된 항목에 한해 쓴다.
- ❌ **테스트 파일(`*.test.ts` / `*.test.tsx`)을 수정하지 않는다.** 보안 점검이 테스트 계약을 바꿀 이유가 없다.
- ✅ **수정은 "즉시 수정 필요"로 분류되고 승인된 항목만.** 권장·무시 항목은 보고만 하고 손대지 않는다.

## 실행 순서

### 1단계 — 타입 오류 수집 (`tsc --noEmit`)

```bash
npx tsc --noEmit
```

- 출력 없이 종료(exit 0)면 타입 오류 0. 이 프로젝트는 pre-commit 훅도 `npm run typecheck`(= 같은 명령)를 돌리므로, **여기서 오류가 있으면 애초에 커밋이 막힌다** → 전부 "즉시 수정 필요"다(빌드 실패 수준).
- 오류가 있으면 파일·라인·메시지를 그대로 수집한다. `strict` + `noUnusedLocals`/`noUnusedParameters`가 켜져 있어 미사용 변수/파라미터도 오류로 잡힌다.

### 2단계 — 의존성 취약점 수집 (`npm audit`)

```bash
npm audit
```

취약점 목록을 수집하되, **분류를 위해 각 항목이 어느 의존성 계층인지**를 함께 본다. 이게 3단계 분류의 핵심 근거다:

- **런타임에 실제 실려 나가는 의존성**인가, 아니면 **dev/빌드 도구**(vite, vitest, json-server, ws, esbuild 등)인가?
- 이 프로젝트는 **백엔드가 json-server 목이고 배포 산출물이 없는 학습용**이다. `vite`/`ws`/`json-server` 같은 dev 서버 의존성의 취약점은 **개발 머신에서만** 관련되며, 사용자에게 배포되는 코드 경로에 없다. 심각도가 critical이어도 이 프로젝트의 위험도는 낮다 — 심각도(severity)와 실제 노출(exposure)은 다르다.
- 판단이 서면 `npm audit --json`으로 각 취약점의 경로(`nodes`)를 확인해 dev-only인지 못박는다.

### 3단계 — 시크릿·환경변수 노출 확인 (grep)

`.env`의 값이나 하드코딩된 시크릿이 **클라이언트 번들로 새는지** 확인한다. Vite 앱에서 클라이언트로 나가는 건 `src/`에 인라인된 문자열과 `import.meta.env.VITE_*` 뿐이다.

```bash
# .env 존재 여부와 내용(참고용)
ls -la .env* 2>/dev/null
# src/에서 환경변수를 클라이언트로 인라인하는지
grep -rn "import.meta.env\|process.env" src/
# 하드코딩된 시크릿 흔적 (키·토큰·비밀번호·자격증명)
grep -rniE "(api[_-]?key|secret|token|password|passwd|credential|private[_-]?key)[\"'[:space:]]*[:=]" src/
```

- **이 프로젝트의 정상 상태**: `.env`가 없고, `src/`에 `import.meta.env`/`process.env` 사용이 없다. `API_URL = 'http://localhost:3001'` 하드코딩은 **의도된 목서버 주소**지 시크릿이 아니다(CLAUDE.md 「api 계층」) → 노출이면 안 되는 값이 아니므로 **무시 가능**.
- **진짜 위험 신호**: `.env`에 정의된 비밀값이 `src/`에서 참조되거나, `VITE_` 접두 변수에 시크릿이 담겼거나(그건 번들에 인라인돼 브라우저에 그대로 노출), API 키·토큰이 `src/`에 문자열로 박혀 있음 → **즉시 수정 필요**.
- `.env`가 없으면 이 단계는 "노출 없음"으로 빠르게 통과하고 그 사실을 보고한다.

### 4단계 — 3단계로 분류해 보고

수집한 모든 결과(타입 오류 + audit + 시크릿)를 아래 세 버킷으로 나눠 개발자에게 보고한다. **분류 근거를 반드시 한 줄로 단다** — 분류가 이 스킬의 핵심 산출물이다.

| 버킷                  | 의미                                        | 이 프로젝트에서의 예                                                                                                      |
| --------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| 🔴 **즉시 수정 필요** | 보안 위험 또는 빌드 실패 수준               | 타입 오류(커밋 차단), 시크릿/키의 클라이언트 노출, 런타임 의존성의 실제 악용 가능 취약점                                  |
| 🟡 **권장 수정**      | 코드 품질·잠재 위험이나 지금 당장 막진 않음 | 하위호환으로 고쳐지는 런타임 의존성 취약점, `dangerouslySetInnerHTML`·`eval` 등 위험 API                                  |
| ⚪ **무시 가능**      | false positive 또는 의도된 패턴             | dev/빌드 전용 의존성(vite·ws·json-server) 취약점, 하드코딩된 localhost `API_URL`, 미사용이 아님이 확실한데 잡힌 린트 오탐 |

보고 형식:

```
## 보안 점검 결과 — 이슈 #{N}

### 🔴 즉시 수정 필요 (N건)
- [타입] src/…:L?? — {메시지} · 근거: 커밋 차단 수준
- [시크릿] … · 근거: VITE_ 변수에 토큰 → 번들 노출

### 🟡 권장 수정 (N건)
- [audit] {패키지} {심각도} — {요약} · 근거: 런타임 의존성, audit fix로 하위호환 해결 가능

### ⚪ 무시 가능 (N건)
- [audit] vite/ws — dev 서버 전용, 배포 경로 없음 · 근거: 목 프로젝트, exposure 없음
- [시크릿] API_URL=localhost — 의도된 목서버 주소(CLAUDE.md)

## 요약: 🔴 N / 🟡 N / ⚪ N
🔴 항목만 수정 대상입니다. 진행할까요?
```

```
[GATE] 개발자 승인 대기 — 승인 전까지 아무것도 고치지 않는다
```

### 5단계 — 승인 후 "즉시 수정 필요"만 처리

승인되면 🔴 버킷만 처리한다. 🟡·⚪는 손대지 않는다(원하면 개발자가 따로 지시한다).

- **타입 오류**: 해당 `src/` 코드를 최소 수정으로 고친다. 테스트 파일은 건드리지 않는다(절대 규칙).
- **의존성 취약점**(🔴로 분류된 경우): `npm audit fix`만 쓴다. `--force` 금지. `audit fix`로 안 되는 건 "수동 대응 필요"로 남기고 임의로 major를 올리지 않는다.
- **시크릿 노출**: 하드코딩된 시크릿을 코드에서 제거하고, 필요하면 `.env`(+ `.gitignore` 확인) 경유로 옮긴다. 이미 커밋 이력에 들어간 시크릿이면 **회전(rotate)이 필요함을 경고**한다 — 코드에서 지워도 git 이력엔 남는다.
- 판단이 애매하면 고치지 말고 개발자에게 되묻는다.

### 6단계 — 재스캔으로 클린 확인

수정한 항목에 해당하는 스캔을 다시 돌려 🔴가 사라졌는지 확인한다:

```bash
npx tsc --noEmit          # 타입 오류 → 0
npm audit                 # 수정한 취약점 해소 확인
npm test                  # 회귀 없는지 (수정이 동작을 안 깨뜨렸는지)
```

- `npm test`를 반드시 다시 돌린다 — 보안 수정이 코드를 바꿨다면 회귀가 없어야 커밋할 수 있다.
- 최종 상태(🔴 = 0, 테스트 통과, 남은 🟡·⚪ 목록)를 개발자에게 보고하고 끝낸다.

## 왜 "분류"가 핵심인가

`npm audit`은 프로젝트 문맥을 모른 채 심각도만 외친다. critical 8건을 그대로 "다 고쳐야 한다"로 받으면, 배포되지도 않는 dev 서버 의존성 때문에 멀쩡한 빌드를 `--force`로 깨뜨리는 최악의 결말로 간다. 보안 점검의 실력은 **exposure(실제 노출 경로가 있는가)를 severity(심각도)와 분리해 판단**하는 데 있다. 이 스킬이 승인 게이트를 두고 "즉시 수정"을 좁게 정의하는 이유가 그것이다.

## 파이프라인에서의 위치

`… → tdd-green → tdd-refactor → **security-review(이 스킬)** → 커밋`. 커밋 직전 마지막 게이트다. pre-commit 훅이 타입체크를 이미 돌리지만, 이 스킬은 거기에 **의존성 취약점·시크릿 노출**을 더하고 결과를 **분류·승인 흐름**으로 다룬다는 점이 다르다.

## 다른 기능에 쓸 때

이 스킬은 특정 기능에 묶이지 않는다 — 프로젝트 전체 상태(타입·의존성·시크릿)를 본다. `$ARGUMENTS`는 어느 이슈 작업 끝에 돌리는지 보고 맥락으로만 쓴다.
