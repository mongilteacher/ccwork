# TDD Green — 실패하는 테스트를 통과시키는 최소 구현

`tdd-red`가 남긴 **실패하는 테스트**를 통과(Green)로 넘긴다. 이 단계의 목표는 "좋은 코드"가 아니라 **"지금 실패하는 테스트를 통과시키는 가장 작은 구현"**이다. 구조 개선·중복 제거는 다음 **Refactor** 단계의 몫이다.

- **입력**: 이슈 번호 `$ARGUMENTS` (예: `/tdd-green 1`)
- **읽을 것**: `docs/features/tag/issue-{N}.md`(시그니처 + 시나리오), 실패한 테스트 파일, `docs/design-system/`(UI일 때)
- **산출물**: `src/`의 구현 코드 (+ 시나리오 문서의 완료 체크)

## 절대 규칙

`tdd-red`의 규칙을 **정확히 뒤집은 것**이다. Red는 테스트 파일만, Green은 구현만 건드린다.

- ✅ **`src/`의 구현 코드만 작성/수정한다.**
- ❌ **테스트 파일(`*.test.ts` / `*.test.tsx`)은 절대 수정하지 않는다.** 테스트가 요구하는 계약이 곧 명세다. 테스트가 통과하기 어렵게 짜였다고 느껴지면 **테스트를 고치지 말고 개발자에게 보고**한다 — 테스트를 손대는 순간 무엇을 검증하는지가 흔들린다.
- ❌ **테스트에 없는 기능을 구현하지 않는다.** 시나리오에 없는 상태·분기·prop·엣지 케이스를 "있으면 좋으니까" 미리 만들지 않는다(YAGNI). 나중 슬라이스(TAG-2/3…)의 몫이다.
- ❌ **불필요한 추상화를 만들지 않는다.** 지금 테스트 하나를 통과시키는 데 팩토리·제네릭·설정 객체가 필요 없으면 만들지 않는다. 반복이 실제로 보일 때 Refactor에서 뽑는다.

### "최소 구현"이 왜 중요한가

Green 단계에서 과하게 만들면 두 가지가 무너진다. 첫째, **테스트가 검증하지 않는 코드**가 섞여 들어와 커버리지가 착시가 된다("초록불인데 안 짜인 로직"). 둘째, 다음 슬라이스가 요구할 형태를 지금 추측하면 대개 틀리고, 그걸 되돌리는 비용이 더 크다. 테스트가 시키는 것만, 시키는 만큼만 짜는 게 TDD가 주는 안전망을 유지하는 길이다.

## 실행 순서

### 1단계 — `npm test`로 실패 목록 확인

```bash
npm test
```

출력에서 두 가지를 읽는다:

- **`Tests` 요약 줄** — 몇 개가 실패(`failed`)했고 총 몇 개가 인식됐는가.
- **개별 실패 메시지** — 각 테스트가 _왜_ 실패하는지(모듈 없음 / 함수 미정의 / 값 불일치 / 렌더 결과 다름).

이 목록이 이번 이슈에서 통과시켜야 할 작업 목록이다.

### 2단계 — collect 실패 감지 → 시그니처 stub 생성

**가장 먼저 확인할 것**: vitest가 보고한 `Tests` 총 수가 시나리오 문서의 시나리오 수와 **일치하는가**.

`docs/features/tag/issue-{N}.md` 하단 `## 테스트 시나리오`의 항목 수를 센다(불릿 `- [정상] …` 또는 체크박스 `- [ ] …` 한 줄 = 시나리오 1개). 이 수보다 vitest의 `Tests` 수가 **적으면 collect 실패**다.

**왜 이런 일이 생기나**: 테스트 파일이 아직 없는 모듈을 `import` 하면(`import { validateTag } from './tag'`), vitest는 그 파일의 `it()`들을 **등록하기도 전에** import 에러로 파일 전체를 통째로 떨군다. 그래서 그 파일 안의 시나리오들이 `Tests` 수에서 아예 빠진다 — "실패"가 아니라 "존재하지 않는 것처럼" 보인다. 이 상태로 개별 테스트를 하나씩 통과시키려 해도 잡을 대상 자체가 안 잡힌다.

**해결**: import 대상 모듈을 **시그니처만 있는 stub**으로 만들어 collect를 성립시킨다. `docs/features/tag/issue-{N}.md` 상단 **확정 시그니처**를 그대로 옮기되, 본문은 비운다.

```ts
// src/domain/tag.ts — stub: 시그니처만, 본문은 최소 placeholder
export type TagError = 'duplicate' | 'tooLong' | 'tooMany';
export function validateTag(value: string, tags: string[]): TagError | null {
  throw new Error('not implemented'); // 4단계에서 채운다
}
```

```tsx
// src/components/TagInput.tsx — stub: 렌더만 뚫려 있으면 됨
interface TagInputProps {
  tags: string[];
}
export function TagInput({ tags }: TagInputProps) {
  return null; // 4단계에서 채운다
}
```

- stub의 목적은 **import가 풀려 전체 테스트가 인식되는 것**뿐이다. 로직은 넣지 않는다(placeholder throw / `return null`).
- `noUnusedParameters`가 켜져 있어 **미사용 파라미터가 빌드 에러**다. stub 파라미터를 안 쓰면 이름 앞에 `_`를 붙이거나, 어차피 4단계에서 바로 채울 테니 그 자리에서 쓰도록 둔다.
- stub 생성 후 다시 `npm test` → 이제 시나리오 수와 `Tests` 수가 맞고, 각 테스트가 **개별적으로 실패**하는 상태가 된다. 여기서부터 하나씩 통과시킨다.
- collect 실패가 없으면(수가 이미 일치) 이 단계는 건너뛴다.

### 3단계 — 디자인 컨텍스트 로드 (UI 구현일 때만)

이번 이슈가 **컴포넌트/JSX를 만들거나 고치면**, 코드를 짜기 전에 시각 스펙을 확보한다. 이 프로젝트는 디자인 정본이 있고, **편집을 자동 검사하는 ratchet 훅**이 있으므로 이 단계를 건너뛰면 4단계에서 편집이 막힌다.

1. **`design-system` 스킬을 먼저 부른다.** 이 프로젝트에는 UI 작업용 `design-system` 스킬이 있고, `docs/design-system/`의 정본(색상·간격·그림자·컴포넌트 규격) 중 **필요한 문서만** 골라 읽어준다. 구현 대상 컴포넌트의 색/간격/상태별 표현을 여기서 파악한다.
   - 정본 위치: `docs/design-system/foundations.md`(토큰), `docs/design-system/components/`(버튼·인풋·카드/리스트·Knowledge Token 규격).
2. **이슈 문서의 "디자인 참고" 섹션**: `docs/features/{feature}/issue-{N}.md`에 해당 섹션이 있으면 함께 읽어 이 슬라이스 특정 스펙을 확인한다.
3. **CLAUDE.md의 스타일링 컨벤션**: 서체 토큰, No-Line Rule, `@theme` 사용 등 프로젝트 규약을 참조한다.
4. **정본이 하나도 없으면** 이 단계를 건너뛰고 CLAUDE.md 컨벤션만 따른다.

> ⚠️ **ratchet 훅 주의**: `.claude/hooks/design-system-check.sh`가 `src/**/*.tsx`·`src/index.css` 편집 시 **새로 추가된 줄**을 검사해 원시 Tailwind 색상, arbitrary 그림자·간격, hex 직접 기입, 인라인 `style`, 테두리 사용을 발견하면 편집을 **차단(exit 2)**한다. 기존 코드 위반은 통과되지만 새 줄은 정본 토큰을 써야 한다. 훅에 막히면 테스트를 느슨하게 하는 게 아니라 **정본 토큰으로 다시 짜서** 통과시킨다.

### 4단계 — 첫 번째 실패 테스트를 최소 구현으로 통과시킨다

실패 목록의 **맨 위 하나**만 고른다. 그 테스트의 `expect`가 요구하는 것만 충족하는 최소 코드를 stub 본문에 채운다.

- 구현은 이 프로젝트의 계층별 규약을 따른다(아래 「구현 컨벤션」). 어느 계층에 무엇을 두는지는 `CLAUDE.md`가 정본이다.
- **UI 컴포넌트**라면 테스트가 요구하는 동작을 충족하되 3단계에서 파악한 **정본 스타일 스펙**(Tailwind 토큰 클래스, 레이아웃 구조, 상태별 표현)을 함께 적용한다. 정본에 명시된 클래스를 **그대로** 쓴다.
- **정본에 없는 시각 요소를 임의로 추가하지 않는다.** 테스트가 요구하지 않고 정본에도 없는 아이콘·애니메이션·여백을 "예뻐 보이려고" 넣지 않는다.

### 5단계 — 실행해서 통과·회귀를 확인한다 (피드백 루프, 최대 5회)

```bash
npm test
```

- **방금 그 테스트가 통과 + 다른 테스트가 새로 깨지지 않았으면** → 6단계로.
- **아직 실패하면**: 에러 메시지를 읽고 **원인을 분석**한다(값이 다른가 / 렌더가 안 됐나 / 비동기 처리 누락인가). 구현을 고치고 이 단계를 **다시 실행**한다.
- **회귀가 생겼으면**(이전에 통과하던 게 깨짐): 방금 변경이 다른 계약을 침범한 것이다. 원인을 찾아 최소 변경으로 양쪽을 만족시킨다.
- **5회 반복해도 통과하지 못하면 멈춘다.** 시나리오·시그니처·테스트 중 무엇과 구현이 어긋나는지 정리해 개발자에게 보고하고 지시를 기다린다. 억지로 통과시키려 테스트를 고치거나 로직을 비틀지 않는다.

빠른 반복을 위해 해당 파일만 돌려도 된다: `npx vitest run <테스트파일경로>`. 단, 6단계로 넘어가기 전 한 번은 `npm test`로 **전체 회귀**를 확인한다.

### 6단계 — 시나리오 문서에 완료 표시

통과시킨 시나리오를 `docs/features/tag/issue-{N}.md`에서 완료로 표시한다.

- 시나리오가 체크박스(`- [ ] …`)면 `- [x] …`로 바꾼다.
- 불릿(`- [정상] …`)이면 줄 끝에 `✅`를 붙이거나 `- [x]`로 변환해 **어디까지 통과했는지 추적 가능**하게 남긴다.

이 표시가 다음 테스트로 넘어갈 때 "무엇이 남았는지"를 알려주는 진행 표시다.

### 7단계 — 다음 실패 테스트로 이동

남은 실패 테스트의 맨 위로 가서 **4단계부터 반복**한다. 실패 목록이 빌 때까지(전부 Green) 계속한다.

### 8단계 — 전체 통과 후 커버리지 측정 (참고용)

모든 테스트가 통과하면 커버리지를 확인한다:

```bash
npx vitest run --coverage
```

- 미커버 라인(리포트의 `Uncovered Line #s`)을 본다.
- 미커버가 **시나리오에서 빠진 케이스**로 보이면 → 개발자에게 보고한다(예: "이 분기는 어떤 시나리오도 안 밟는다").
- ❌ **커버리지를 올리려고 테스트를 추가하지 않는다.** 커버리지는 **참고 지표**일 뿐이다. 테스트 추가는 시나리오 도출(`test-scenarios`)·Red(`tdd-red`) 단계의 몫이지 Green이 임의로 늘리는 게 아니다. 미커버는 "빠진 시나리오"의 신호로만 쓴다.

> 커버리지 도구(`@vitest/coverage-v8`)가 설정돼 있어야 한다. 없으면 개발자에게 알린다(`npm i -D @vitest/coverage-v8`).

### 9단계 — 결과 요약

개발자에게 보고한다:

- **통과시킨 테스트 수 / 전체** (예: "8/8 Green").
- **만든/수정한 `src/` 파일 목록**과 각 파일에서 채운 것(한 줄씩).
- **stub → 구현으로 채운 흐름**(collect 실패가 있었으면 그 처리 포함).
- **커버리지 미커버 중 시나리오 누락 의심 지점**(있으면).
- **5회 루프로도 못 넘긴 테스트**(있으면, 원인과 함께).

## 이 프로젝트 구현 컨벤션 (요지 — 정본은 CLAUDE.md)

계층별로 무엇을 어디에 두는지가 고정돼 있다. 최소 구현도 이 규약 안에서 한다.

- **도메인**(`src/domain/*`) — React·fetch·DOM 무의존 순수 함수. 검증 실패는 **throw가 아니라 에러 코드 반환**(`TagError` 등). 사용자 문구는 모른다(UI가 매핑).
- **api**(`src/api/notes.ts`) — `export async function verbNoun(...): Promise<T>`(화살표 금지). `res.ok` 검사 후 `throw new Error('Failed to …')`. 타임스탬프는 api가 주입. 정규화·검증은 넣지 않는다.
- **Context**(`src/context/NotesContext.tsx`) — mutation 이름은 api와 동일. 성공 후 `setNotes` 낙관적 갱신(재fetch 없음). 초기 로드 실패만 `error` state로 흡수, mutation은 throw 그대로.
- **컴포넌트**(`src/components/*`) — `interface XxxProps`를 컴포넌트 바로 위에. 데이터는 `useNotes()`로 당기고 props는 선택 상태·콜백만. 콜백 prop `on`+동사 / 구현체 `handle`+동사. 폼 검증 실패는 입력 아래 인라인 한 줄(`text-destructive text-xs`), `onChange`에서 지운다. `alert`/`confirm` 금지, 서버 실패는 `console.error`만.

확신이 안 서면 추측하지 말고 해당 파일과 CLAUDE.md의 해당 절을 읽어 맞춘다.

## 파이프라인에서의 위치

`feature-planner`(기획) → `test-scenarios`(시그니처·시나리오) → `tdd-red`(실패 테스트) → **`tdd-green`(이 스킬, 최소 구현)** → Refactor(구조 개선). Green은 "테스트가 시키는 대로 통과"까지만이다. 통과한 뒤의 중복 제거·이름 정리는 Refactor에서 하며, 그때도 테스트가 계속 초록불인지로 안전을 확인한다.

## 다른 기능에 쓸 때

경로의 `tag`는 현재 태그 기능 기준이다. 다른 기능이면 `docs/features/{그 기능}/issue-{N}.md`로 바꾸고, 그 기능에 디자인 참고가 없으면 3단계는 CLAUDE.md 컨벤션만 따른다.
