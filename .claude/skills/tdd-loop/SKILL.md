# TDD Loop — 이슈 하나를 7단계로 관통시킨다

CLAUDE.md의 「TDD 이슈 사이클」을 사람이 매번 손으로 이어붙이지 않도록 묶은 **컨테이너**다.

이 스킬 자체는 코드를 한 줄도 쓰지 않는다. 하는 일은 셋뿐이다:

1. 시작 전 안전 점검과 브랜치 준비
2. 7단계를 **정해진 순서로** 호출
3. 어딘가 멈추면 **어디서 왜 멈췄는지** 분명히 알리고 중단

- **입력**: GitHub 이슈 번호 `$ARGUMENTS` (예: `/tdd-loop 12`)
- **산출물**: 이슈를 닫는 PR 하나. 중간 산출물은 각 하위 스킬이 만든다

## 이 컨테이너의 성격

**게이트를 더하지 않는다.** 각 하위 스킬에는 이미 승인 게이트가 있다(시그니처 확정, 시나리오 확정, 리팩터 대상 승인, 보안 수정 승인, PR 초안 승인). 그 게이트들은 그대로 작동하며, 사용자가 답해야 다음으로 간다.

컨테이너가 여기에 "이제 Green 단계로 갈까요?" 같은 확인을 하나 더 얹으면, 원래 5번이면 될 응답이 12번이 된다. **단계 사이에는 진행 상황 한 줄만 출력하고 바로 다음 스킬을 부른다.** 사용자가 멈추고 싶으면 하위 스킬의 게이트에서 멈추면 된다.

**스스로 대신하지 않는다.** 하위 스킬이 할 일을 컨테이너가 "빠르니까" 직접 처리하면 그 스킬의 규칙(테스트 파일만 건드린다, 구현만 건드린다 같은 것)이 통째로 사라진다. 각 단계는 반드시 Skill 도구로 해당 스킬을 호출해서 진행한다.

---

## 0단계 — 사전 점검과 브랜치 준비

여기서 걸러내지 못한 문제는 3~4단계쯤에서 훨씬 비싼 형태로 드러난다. 순서대로 확인한다.

### 0-1. 이슈를 읽는다

```bash
gh issue view $ARGUMENTS --repo mongilteacher/ccwork
```

**`--repo`를 반드시 붙인다.** 이 저장소에는 `origin`(mongilteacher/ccwork)과 `upstream`(원본) 두 리모트가 있어서, 생략하면 gh가 upstream을 골라 **번호는 같지만 전혀 다른 이슈**를 읽는다. 조용히 잘못된 AC로 7단계를 도는 것이 이 가드가 막으려는 사고다. 같은 이유로 이 스킬에서 부르는 모든 `gh issue`·`gh pr` 명령에 `--repo`를 붙인다.

(`gh repo set-default mongilteacher/ccwork`를 한 번 실행해 두면 생략해도 안전해지지만, 스킬은 그 설정에 기대지 않는다 — 새로 클론한 사람에게는 설정이 없다.)

본문과 **Acceptance Criteria**를 확인한다. 이슈가 없거나 접근이 안 되면 여기서 중단한다 — 이후 모든 단계가 AC를 기준으로 돌아가므로 AC 없이는 시작할 수 없다.

이슈에 **선행 이슈**가 적혀 있으면 그것이 닫혔는지 확인하고, 아직 열려 있으면 사용자에게 알린다. 선행 이슈의 산출물 위에 얹히는 슬라이스라면 순서를 어기는 순간 헛일이 된다.

### 0-2. 작업 트리가 깨끗한지 본다

```bash
git status --short
```

커밋되지 않은 변경이 있으면 **중단하고 사용자에게 알린다.** 브랜치를 옮기는 순간 그 변경이 새 브랜치로 따라오고, 마지막에 PR을 만들 때 이번 이슈와 무관한 파일이 섞인다. 무엇이 남아 있는지 목록으로 보여주고, 커밋할지 stash할지는 사용자가 정한다.

### 0-3. 분기 지점을 확인한다

```bash
git branch --show-current
```

CLAUDE.md의 사이클은 이슈 브랜치를 **`feature/<spec>`에서 분기**한다(PR base도 거기다). 현재 브랜치가 `feature/<spec>` 형태가 아니면 사용자에게 알리고 어디서 분기할지 확인한다. `main` 위에 서 있는 경우가 흔한데, 그대로 진행하면 PR base가 어긋난다.

이 값은 7단계까지 들고 간다 — **PR의 base 브랜치가 된다.**

### 0-4. 이슈 브랜치를 만든다

브랜치 이름은 `feat/<issue-slug>` 형태로 짓는다. 슬러그는 이슈 제목에서 뽑되 짧고 영문으로 만든다(예: 이슈 #12 "TF-1 사이드바에 태그 목록 표시" → `feat/tf-1-tag-list`).

```bash
git checkout -b feat/<issue-slug>
```

**이미 같은 이름의 브랜치가 있으면** 같은 이슈를 다시 도는 것으로 본다. 임의로 덮어쓰지 말고 사용자에게 묻는다:

> `feat/tf-1-tag-list` 브랜치가 이미 있습니다. 이전에 이 이슈를 진행하신 것 같습니다.
> ① 그 브랜치로 이어서 진행 ② 새로 시작(기존 브랜치 삭제) ③ 취소
> 어떻게 할까요?

②를 고르면 그 브랜치의 커밋이 사라지므로, 삭제 전에 무엇이 들어 있는지(`git log --oneline <branch>`) 보여주고 확인받는다.

### 0-5. 준비 완료를 알린다

점검 결과를 짧게 요약한다 — 이슈 제목, AC 개수, 분기 지점, 새 브랜치 이름. 그리고 **바로 1단계로 넘어간다.** 여기서 "시작할까요?"라고 묻지 않는다(사용자가 이미 이 스킬을 호출해 시작을 요청했다).

## 1~7단계 — 순서대로 호출한다

각 단계 앞에 아래 형식으로 한 줄 진행 표시를 출력하고, 바로 해당 스킬을 호출한다.

```
━━ [3/7] Green — 최소 구현으로 테스트 통과 ━━
```

| #   | 호출 대상                     | 하는 일                              | 그 안의 게이트               |
| --- | ----------------------------- | ------------------------------------ | ---------------------------- |
| 1   | `/test-scenarios $ARGUMENTS`  | 시그니처 확정 → 테스트 시나리오 도출 | 시그니처 승인, 시나리오 승인 |
| 2   | `/tdd-red $ARGUMENTS`         | 시나리오를 실패하는 테스트로 변환    | —                            |
| 3   | `/tdd-green $ARGUMENTS`       | 최소 구현으로 통과. 회귀 감시        | —                            |
| 4   | `@ac-verifier` (Agent)        | AC 충족 독립 검증                    | 갭 보고                      |
| 5   | `/tdd-refactor $ARGUMENTS`    | 구조 개선. 변경마다 `npm test`       | 리팩터 대상 승인             |
| 6   | `/security-review $ARGUMENTS` | 타입·의존성·시크릿 점검              | 수정 항목 승인               |
| 7   | `/create-pr`                  | E2E 게이트 → push → PR 생성          | PR 초안 승인                 |

### 단계별로 컨테이너가 챙길 것

**2단계(Red)** — 모듈이 아직 없어 테스트 수집(collect) 자체가 실패하는 것은 이 단계에서 **정상**이다. Red 스킬이 그 상태를 남기고 끝내면 그대로 3단계로 넘어간다. 컨테이너가 stub을 만들어 "고쳐주지" 않는다 — 그건 Green의 일이다.

**4단계(AC 검증)** — `ac-verifier`는 서브에이전트다. Agent 도구로 `subagent_type: "ac-verifier"`, 프롬프트에 이슈 번호를 넘겨 호출한다. 결과가 **AC 갭을 보고하면 5단계로 진행하지 않고 사용자에게 보여주며 멈춘다.** 테스트가 전부 초록이어도 AC를 놓쳤을 수 있고, 그걸 발견하는 것이 이 단계의 존재 이유다. 갭을 메우려면 시나리오를 보강해 2~3단계를 다시 도는 것이 정석이므로, 어디로 돌아갈지는 사용자가 정한다.

**6단계(보안 점검)** — "즉시 수정 필요" 항목이 남아 있으면 7단계로 넘기지 않는다. 스킬이 승인받아 수정을 마친 뒤 진행한다.

**7단계(PR)** — `create-pr`에는 자체 E2E 게이트가 있어 실패하면 PR을 만들지 않고 멈춘다. 그 판단을 존중하고 우회하지 않는다. PR 생성 시 컨테이너가 챙길 세 가지:

- **base 브랜치는 0-3에서 확인한 `feature/<spec>`** — `main`이 아니다
- **PR 본문에 `Closes #$ARGUMENTS`** — PR과 이슈를 연결한다. 단 **이것만으로는 이슈가 닫히지 않는다**: GitHub은 PR이 _기본 브랜치(main)로_ 머지될 때만 자동 클로즈하는데, 이 사이클의 base는 `feature/<spec>`이다. 머지 후 `gh issue close $ARGUMENTS --repo mongilteacher/ccwork`가 따로 필요하다는 것을 개발자에게 알린다
- PR 생성 후 **이슈에 PR 링크를 코멘트**로 남긴다:
  ```bash
  gh issue comment $ARGUMENTS --repo mongilteacher/ccwork --body "PR: <생성된 PR URL>"
  ```

커밋은 commitlint를 통과해야 한다(제목 `<type>: <한국어 제목>`, 빈 줄, **본문 내용 2줄 이상, 각 줄 100자 이하**). 훅에 걸려 커밋이 거절되면 메시지를 고쳐 다시 시도한다 — `--no-verify`로 우회하지 않는다.

## 멈출 때

어느 단계에서든 진행이 불가능해지면 **조용히 넘어가지 말고 멈춘다.** 다음 형식으로 알린다:

```
⛔ [4/7] AC 검증에서 중단

무엇이: AC 3번("카운트가 같으면 가나다순")에 해당하는 구현이 없습니다.
왜: countTags가 카운트 내림차순만 정렬하고 동점 처리를 하지 않습니다.
지금 상태: feat/tf-1-tag-list 브랜치, 커밋 2개, 테스트 14개 통과
다음: 시나리오에 동점 케이스를 추가하고 /tdd-red 12 → /tdd-green 12 를 다시 도세요.
```

**이 네 줄이 핵심이다** — 무엇이 / 왜 / 지금 상태 / 다음. 특히 "지금 상태"가 있어야 사용자가 브랜치를 확인하지 않고도 이어갈 지점을 안다.

중단은 실패가 아니라 설계된 동작이다. 남은 단계를 억지로 밀어붙여 PR까지 만들면, 문제가 리뷰어에게 넘어갈 뿐 사라지지 않는다.

## 이어서 돌리기

중단된 뒤 사용자가 문제를 해결하고 돌아오면, 처음부터 다시 돌릴 필요가 없다. **끝난 단계는 건너뛰고 멈춘 단계부터** 재개한다. 어디까지 됐는지는 이렇게 확인한다:

- `docs/features/{기능}/issue-{N}.md`가 있고 시나리오가 채워져 있으면 → 1단계 완료
- 해당 테스트 파일이 있으면 → 2단계 완료
- `npm test`가 초록이면 → 3단계 완료
- 이미 커밋이 쌓여 있으면 → 5~6단계 진행 중이었을 가능성

애매하면 사용자에게 어디부터 재개할지 묻는다. 되돌아가서 다시 하는 비용보다, 잘못된 지점에서 이어붙이는 비용이 크다.
