# TDD Refactor — 초록불을 유지하며 구조만 개선

`tdd-green`이 테스트를 통과시킨 뒤, **동작을 하나도 바꾸지 않으면서** 코드 구조를 다듬는 단계다. 테스트가 안전망이다 — 리팩토링이 동작을 바꿨다면 초록불이 빨간불로 변해 즉시 알려준다. 그러니 이 단계의 규율은 단순하다: **작게 바꾸고, 매번 테스트를 돌리고, 깨지면 되돌린다.**

- **입력**: 이슈 번호 `$ARGUMENTS` (예: `/tdd-refactor 1`)
- **읽을 것**: `CLAUDE.md`(컨벤션 정본), 이번 이슈가 바꾼 `src/` 파일
- **산출물**: 구조가 개선된 `src/` 코드 (동작·공개 계약 불변) + 전후 요약

## 절대 규칙

리팩토링의 정의는 "**겉보기 동작을 바꾸지 않고 내부 구조를 개선**"이다. 이 정의에서 아래가 따라 나온다:

- ❌ **새 기능을 추가하지 않는다.** 새 분기·prop·상태·엣지 케이스 처리를 넣지 않는다. 그건 리팩토링이 아니라 기능 변경이고, 그걸 검증할 테스트가 지금 없다.
- ❌ **테스트 파일(`*.test.ts` / `*.test.tsx`)을 수정하지 않는다.** 테스트는 "동작이 안 바뀌었다"를 증명하는 기준점이다. 기준점을 움직이면 증명이 무너진다. 테스트가 리팩토링을 방해하면(예: 내부 구현에 지나치게 결합) **고치지 말고 개발자에게 보고**한다.
- ❌ **`src/` 밖을 수정하지 않는다.** `db.json`·설정·문서·하네스는 이 단계 범위가 아니다.
- ❌ **대상 파일 범위(3단계 `git diff` 결과) 밖을 수정하지 않는다.** 이번 이슈가 건드리지 않은 파일이나 새 파일 생성은 범위 밖이다. 파일을 가로질러 추출하고 싶으면(예: 공용 헬퍼를 새 모듈로) **실행하지 말고 제안으로 남긴다**(7단계).

### 왜 이렇게 좁히나

리팩토링은 "손대는 김에" 범위가 무한히 번지기 쉽다. 이번 이슈 범위로 좁히면 두 가지를 얻는다. 첫째, **리뷰가 쉬워진다** — diff가 이슈와 1:1로 대응한다. 둘째, **안전하다** — 이번 이슈의 테스트가 덮는 코드만 만지므로, 초록불이 "동작 불변"을 실제로 보증한다. 범위 밖 코드는 이 이슈의 테스트가 지켜주지 못한다.

## 실행 순서

### 1단계 — CLAUDE.md로 컨벤션 파악

`CLAUDE.md`를 읽어 이 프로젝트의 정본 규약을 머리에 넣는다. 리팩토링의 "개선" 방향이 곧 이 컨벤션이다:

- **네이밍** — 콜백 prop `on`+동사 / 구현체 `handle`+동사, api 함수 `동사+Note(s)`, Context mutation은 api와 동명, boolean은 `is`/동명사.
- **계층 책임** — 도메인(순수·에러코드 반환) / api(fetch 래퍼·throw) / Context(낙관적 갱신) / 컴포넌트(UI만). 로직이 엉뚱한 계층에 있으면 옮기는 게 리팩토링이다.
- **컴포넌트 구조** — `interface XxxProps` 상단, early return 분기, 파생값은 `useMemo` 없이, 조건부 className은 템플릿 리터럴+삼항.
- **알려진 불일치** — CLAUDE.md의 「알려진 불일치」는 정리 후보 목록이다. 단, **이번 이슈 대상 파일 안에 있을 때만** 손댄다(절대 규칙 4번).

### 2단계 — `npm test`로 시작 상태가 초록불인지 확인

```bash
npm test
```

**전부 통과하는 것을 먼저 확인한다.** 리팩토링은 초록불에서 시작해 초록불로 끝나는 작업이다. 시작부터 빨간불이면 리팩토링할 상태가 아니다 — Green 단계가 안 끝난 것이므로 개발자에게 알리고 멈춘다. 이 통과 상태가 이후 모든 변경의 기준선이다.

### 3단계 — 리팩토링 대상 파일 식별

이번 이슈가 바꾼 `src/` 파일만 대상으로 뽑는다:

```bash
git diff main...HEAD --name-only -- src/ | grep -v '\.test\.'
```

- `main...HEAD`(점 3개)는 **분기가 갈라진 지점 이후 이번 브랜치의 변경**만 본다. 이게 "이번 이슈가 건드린 파일"이다.
- `grep -v '\.test\.'`로 테스트 파일을 뺀다(절대 규칙 2번 — 테스트는 안 만진다).
- 남은 파일들을 아래 **범용 점검 기준**으로 검토한다.

#### 범용 점검 기준 (스킬 내장)

각 대상 파일을 이 다섯 눈으로 본다. 발견을 "무엇을 / 어디서 / 왜 / 어떻게 고칠지"로 기록한다:

1. **중복 제거** — 같은 로직이 두 번 이상 반복되는가. (단, 우연히 닮은 코드를 성급히 묶지 않는다 — 반복이 "같은 이유로 함께 변한다"고 확신될 때만.)
2. **네이밍 명확성** — 이름이 의도를 드러내는가. 약어·모호한 `data`/`tmp`·역할과 어긋난 이름.
3. **단일 책임** — 한 함수/컴포넌트가 너무 많은 일을 하는가. 렌더와 계산이 뒤섞였거나, 계층 경계를 넘는 로직.
4. **불필요한 복잡도** — 매직 넘버, 과도한 중첩, 지금 쓰이지도 않는 추상화(YAGNI 위반), 죽은 코드.
5. **CLAUDE.md 컨벤션 불일치** — 1단계에서 읽은 프로젝트 패턴과 어긋나는 코드.

**고칠 게 없으면 없다고 보고하고 멈추는 것도 정답이다.** 개선을 지어내는 순간(불필요한 추상화 추가 등) 그 자체가 절대 규칙 위반이다. TAG-1처럼 이미 최소하게 짜인 슬라이스는 리팩토링할 게 거의 없는 게 정상이다.

### 4단계 — 대상 목록 보고 → 승인 대기 (게이트)

발견한 리팩토링 대상을 개발자에게 **목록으로** 보여주고 검토받는다. 각 항목에 파일·라인·점검기준 분류·제안 변경을 적는다. 예:

```
리팩토링 대상 (이슈 #{N})
1. [중복] NoteEditor.tsx:L?? — 폼 초기화 로직이 selectedNote/isCreating 분기에서 반복
   → 공통 초기화 헬퍼로 묶기 (파일 내부, 동작 불변)
2. [컨벤션] NotesContext.tsx:L?? — ...
발견 없음: TagInput.tsx (이미 최소 구현)
```

```
[GATE] 개발자가 대상 목록을 승인할 때까지 대기 (승인 전까지 코드를 바꾸지 않는다)
```

승인 없이 5단계로 달리지 않는다. 개발자가 일부만 고르거나 제외할 수 있다 — 그 결정을 따른다.

### 5단계 — 한 번에 하나씩: 변경 → `npm test` → 통과 → 다음

승인된 항목을 **하나씩** 처리한다. 한 항목을 고쳤으면 바로:

```bash
npm test
```

- **전부 통과하면** → 그 변경은 안전하다. 다음 항목으로.
- 여러 항목을 몰아서 바꾼 뒤 한꺼번에 돌리지 않는다 — 깨졌을 때 어느 변경이 원인인지 잃는다. **하나의 논리적 변경 = 한 번의 테스트**가 리듬이다.
- 빠른 반복엔 해당 파일만 돌려도 되지만(`npx vitest run <경로>`), 항목을 끝낼 때 한 번은 `npm test`로 **전체 회귀**를 본다.

> ⚠️ **design-system 훅 주의(.tsx 리팩토링)**: `.claude/hooks/design-system-check.sh`는 편집으로 **새로 추가된 줄**을 검사한다. 기존 위반 코드를 리팩토링하다 그 줄을 옮기면(= diff상 새 줄) 원시 색상·arbitrary 그림자/간격·테두리 등이 **차단(exit 2)**될 수 있다. 이때 "동작 불변"만 지키는 리팩토링이라면, 그 줄을 정본 토큰으로 바꿔 통과시킨다 — 단 이는 시각적 변화를 낳을 수 있으니 4단계에서 그런 항목은 "스타일 마이그레이션 동반"으로 표시해 승인받는다. 애매하면 그 항목은 손대지 말고 제안(7단계)으로 남긴다.

### 6단계 — 깨지면 즉시 롤백 후 다른 접근

`npm test`가 빨간불이 되면, 방금 그 변경이 동작을 바꾼 것이다. **고치려 덧대지 말고 되돌린다** — 리팩토링은 동작을 보존해야 하는데 이미 실패했으므로, 그 접근 자체가 틀렸다.

- 방금 변경만 되돌린다. 그 파일이 이번 이슈에서 커밋된 상태라면 `git checkout -- <파일>`로 마지막 커밋 상태로 복원하고(다른 미커밋 리팩토링이 같은 파일에 없을 때), 아니면 방금 편집을 손으로 원복한다.
- 되돌린 뒤 `npm test`로 초록불 복귀를 확인한다.
- 그 항목은 **다른 접근으로 다시 시도**하거나, 두 번 실패하면 "리팩토링으로 안전하게 안 됨"으로 판단해 건너뛰고 7단계 보고에 남긴다.

> 팁: 승인된 항목이 여러 개라 롤백 단위를 깔끔히 하고 싶으면, 각 항목을 통과시킬 때마다 `refactor: ...`로 작은 체크포인트 커밋을 만들어 두면 롤백이 `git reset`/`checkout`으로 명확해진다(커밋 여부는 개발자 취향).

### 7단계 — 리팩토링 전후 요약

개발자에게 보고한다:

- **적용한 리팩토링 목록** — 파일·무엇을·왜(점검기준 분류). "동작 불변"임을 테스트 결과로 뒷받침.
- **최종 `npm test` 결과** — 시작과 동일하게 전부 통과인지(테스트 수가 그대로여야 한다 — 늘거나 줄면 테스트를 건드렸거나 동작이 바뀐 것).
- **건너뛴 항목** — 롤백했거나 훅에 막혔거나 승인에서 빠진 것, 그 이유.
- **범위 밖 제안** — 대상 파일을 가로지르는 추출, 새 모듈 분리, 다른 이슈의 코드 정리 등 이 단계에서 **일부러 안 한** 것들. 개발자가 다음에 판단하도록 목록으로만 남긴다.

## 파이프라인에서의 위치

`feature-planner` → `test-scenarios` → `tdd-red`(실패 테스트) → `tdd-green`(최소 구현) → **`tdd-refactor`(이 스킬, 구조 개선)**. Green이 "일단 통과"라면 Refactor는 "통과를 유지하며 정리"다. 둘을 나누는 이유: 통과와 정리를 동시에 하면 무엇이 동작을 바꿨고 무엇이 구조만 바꿨는지 뒤섞여, 회귀의 원인을 짚기 어려워진다. Refactor 단계에서 테스트는 **한 줄도 새로 쓰지 않는다** — 오로지 기존 초록불을 나침반으로 쓴다.

## 다른 기능에 쓸 때

이 스킬은 경로에 특정 기능명을 박아두지 않는다 — `git diff main...HEAD`가 대상 파일을 자동으로 찾으므로 어느 기능이든 그대로 쓴다. 기준 분기가 `main`이 아니면(`develop` 등) 그 이름으로 바꾼다.
