# 태그 필터링 PRD

> 이 기능이 궁금하면 여기만 보면 된다. 확정 요구사항은 [`spec-fixed.md`](spec-fixed.md), 최초 아이디어는 [`spec-original.md`](spec-original.md).

## 1. 개요

노트에 붙인 태그를 사이드바 상단에 모아 보여주고, 태그를 클릭하면 **그 태그를 가진 노트를 강조**한다.

핵심은 "숨기지 않는다"는 것이다. 일반적인 필터는 대상 외 항목을 목록에서 제거하지만, 이 기능은 전체 목록을 그대로 둔 채 관심 대상만 도드라지게 한다. 사용자가 전체 맥락을 잃지 않으면서 특정 주제를 찾게 하는 것이 목적이다.

**범위**: 기존 태그 데이터(`Note.tags`)를 읽기만 한다. 태그를 만들거나 고치는 일은 기존 태그 기능([`docs/features/tag/`](../tag/prd.md))의 몫이며 이 기능은 스키마도 API도 바꾸지 않는다.

## 2. 사용자 스토리

### US-1. 태그를 눌러 관련 노트를 찾는다

> 노트가 쌓인 사용자로서, 특정 주제의 노트가 목록 어디에 있는지 훑어 찾는 대신 태그를 눌러 한눈에 보고 싶다.

**인수 조건**

- 사이드바 상단에 전체 노트의 태그가 카운트와 함께 표시된다 (`#회의 3`)
- 태그를 클릭하면 그 태그를 가진 노트가 강조된다
- 강조되지 않은 노트도 목록에 그대로 남아 있다

### US-2. 다른 태그로 갈아타거나 전체로 돌아온다

> 태그를 하나 눌러 본 사용자로서, 다른 태그를 보거나 원래대로 돌아가는 방법이 분명했으면 좋겠다.

**인수 조건**

- 다른 태그를 클릭하면 이전 선택이 해제되고 새 태그가 선택된다
- 선택된 태그를 다시 클릭하면 선택이 해제되어 아무것도 강조되지 않는다
- 지금 어떤 태그가 선택돼 있는지 칩만 보고 알 수 있다

### US-3. 태그를 고쳐도 필터가 어긋나지 않는다

> 노트를 편집하는 사용자로서, 태그를 지우거나 노트를 삭제했을 때 필터가 이상한 상태로 남지 않았으면 좋겠다.

**인수 조건**

- 노트를 저장하면 태그 목록과 카운트가 즉시 반영된다
- 선택한 태그를 가진 노트가 하나도 없게 되면 선택이 자동으로 해제된다
- 태그가 하나도 없으면 태그 영역 자체가 보이지 않는다

## 3. 기술 결정

### ADR-1. 선택 태그는 App의 로컬 state로 두고, 집계·판정은 도메인 순수 함수로 뺀다

**Context**
필터 상태(`selectedTag`)를 어디에 둘지 정해야 한다. 후보는 ① `App.tsx` 로컬 state + `src/domain/tagFilter.ts` 순수 함수, ② `NotesContext` 확장, ③ 전용 `TagFilterContext` 신설이었다. 이 앱의 `NotesContext`는 **서버 데이터의 단일 소스**이고, 화면 전용 상태(`selectedNoteId`, `isCreating`)는 `App.tsx`가 로컬로 들고 props로 내려보내는 구조다.

**Decision**
①을 택한다.

- `selectedTag: string | null`은 `App.tsx`의 `useState`가 소유하고, `TagFilterBar`와 `NoteList`에 props로 내려간다.
- 태그 집계(`countTags`)와 강조 판정(`isHighlighted`)은 `src/domain/tagFilter.ts`에 **React·fetch·DOM을 모르는 순수 함수**로 둔다.
- `NotesContext`와 `src/api/notes.ts`는 **한 줄도 바뀌지 않는다.**

**Alternatives**

- **② `NotesContext` 확장** — 거부. `TagFilterBar`가 props 없이 `useNotes()`만으로 동작해 호출부는 간결해지지만, 그 대가로 Context가 서버 상태와 UI 상태를 겸하게 된다. CLAUDE.md의 "컴포넌트 로컬 state는 UI 전용만 가진다"는 규약을 정확히 반대로 뒤집는 셈이고, 이후 모든 관련 컴포넌트 테스트에 Provider 래핑이 강제된다(코드베이스가 "비용이 크다"고 명시한 것).
- **③ 전용 `TagFilterContext`** — 거부. ②의 관심사 혼합 문제는 풀지만, 이 코드베이스에 Provider 중첩 전례가 없어 도입 비용이 이득보다 크다. 상태가 하나(`string | null`)뿐이라 Provider가 나르는 값보다 Provider 자체가 무겁다. 다중 선택·URL 동기화까지 커지면 그때 옮긴다.

**Consequences**

- (+) `selectedNoteId`와 완전히 같은 취급이라 새 개념을 학습할 필요가 없다.
- (+) 집계·판정이 jsdom 없이 검증되는 도메인 테스트 1순위 대상이 된다. 대소문자 병합 같은 규칙을 `it.each` 표로 명세와 1:1 대응시킬 수 있다.
- (+) `NoteItem`이 props만 받는 순수 컴포넌트로 남아 테스트가 싸다.
- (−) `App → NoteList → NoteItem`으로 prop이 한 단계 더 내려간다. 계층이 더 깊어지면 prop drilling이 부담이 될 수 있으나, 현재 깊이는 2단계다.
- (−) 태그 목록을 다른 화면에서도 쓰게 되면 상태를 끌어올리는 리팩터가 필요하다.

### ADR-2. 필터는 "강조"다 — 숨기지도 정렬하지도 않는다

**Context**
"필터"라는 말은 보통 대상 외 항목을 목록에서 제거하는 동작을 뜻한다. 하지만 이 기능의 사용자는 노트 수십 개를 한 사이드바에서 보며 작업하는 사람이고, 목록이 갑자기 2개로 줄면 "나머지가 어디 갔지"라는 인지 비용이 생긴다.

**Decision**
선택 태그를 가진 노트에 **시각적 강조만** 준다. 비대상 노트는 목록에 그대로 남고, **순서도 바뀌지 않는다.** `NoteList`의 "노트 N개"도 전체 개수를 유지한다.

**Alternatives**

- **숨김 방식** — 거부. 찾기는 가장 빠르지만 전체 맥락이 사라진다. 사용자가 원한 것도 "강조"였다.
- **강조 + 상단 정렬** — 거부. 찾기 쉬움과 맥락 유지를 절충하지만, 목록 순서가 바뀌면 "아까 그 노트가 있던 위치"라는 공간 기억이 깨진다. 클릭할 때마다 목록이 재배열되는 것은 오히려 산만하다.

**Consequences**

- (+) 필터를 켜고 끄는 동안 목록이 요동치지 않아 위치 감각이 유지된다.
- (+) `notes` 배열을 그대로 렌더하므로 목록 렌더 로직이 바뀌지 않는다.
- (−) 노트가 아주 많아지면(수백 개) 강조된 것을 스크롤로 찾아야 해 이점이 줄어든다. 그때는 숨김 방식이나 정렬을 다시 검토한다 — 판정 함수는 그대로 재사용할 수 있다.
- (−) "필터"라는 이름과 실제 동작이 미묘하게 다르므로, 용어를 문서에 못 박아 둔다(§5).

### ADR-3. 선택 태그의 자동 해제는 state 동기화가 아니라 파생값으로 처리한다

**Context**
선택한 태그를 가진 마지막 노트가 삭제되거나 그 노트에서 태그가 지워지면, 사이드바에서 칩이 사라진다. 이때 `selectedTag`가 그대로 남으면 **해제할 방법이 없는 상태**가 된다(누를 칩이 없으므로).

가장 먼저 떠오르는 해법은 `useEffect`로 `notes`를 감시하다 태그가 사라지면 `setSelectedTag(null)`을 부르는 것이다. 하지만 이 앱에는 이미 `NoteEditor`의 폼 동기화 `useEffect`가 있고, 의존성 배열을 일부러 좁혀 `eslint-disable`을 붙여 둘 만큼 다루기 까다로운 코드다. 같은 종류를 하나 더 늘리고 싶지 않다.

**Decision**
`selectedTag`를 state에서 지우지 않는다. 대신 **렌더 시점에 파생**한다:

> 태그 목록에 존재하지 않는 선택 태그는 "선택되지 않은 것"으로 본다.

`isHighlighted`가 태그 목록 기준으로 판정하므로, 노트가 바뀌면 다음 렌더에서 강조가 자동으로 사라진다. 동기화 코드도, 여분의 렌더도 없다.

**Alternatives**

- **`useEffect` + `setSelectedTag(null)`** — 거부. 상태를 고치는 이펙트는 렌더를 한 번 더 유발하고, 의존성 배열을 잘못 잡으면 조용히 깨진다. "화면에서 계산할 수 있는 것을 state에 복제하지 않는다"는 원칙에도 어긋난다.
- **태그 삭제·노트 삭제 핸들러에서 직접 해제** — 거부. 태그가 사라지는 경로가 여럿(노트 삭제, 태그 제거, 태그 수정)이라 한 군데라도 빠뜨리면 버그가 된다. 경로마다 같은 처리를 반복해야 한다.

**Consequences**

- (+) 태그가 사라지는 모든 경로가 코드 한 줄 없이 자동으로 처리된다.
- (+) 판정이 순수 함수라 "선택 태그가 목록에 없을 때" 케이스를 단위 테스트로 직접 찍을 수 있다.
- (−) `selectedTag` state에는 이미 사라진 태그 문자열이 남아 있을 수 있다. 화면과 state가 정확히 일치하지 않으므로, 디버깅할 때 state만 보고 판단하면 헷갈릴 수 있다. 이 점을 함수 주석에 남긴다.
- (−) 사라진 태그가 나중에 다시 생기면(다른 노트에 같은 태그 추가) 선택이 되살아난다. 노트를 지웠다 되돌리는 흐름이 없으므로 실질적 문제는 아니지만, 의도된 동작임을 문서에 남긴다.

### ADR-4. 대소문자가 다른 같은 태그는 하나로 합쳐 집계한다

**Context**
`Note.tags`에는 사용자가 입력한 문자가 그대로 저장된다. 기존 `validateTag`는 **한 노트 안에서는** 대소문자를 무시해 중복을 막지만(`React`가 있으면 `react` 추가 불가), 서로 다른 노트에는 `React`와 `react`가 각각 존재할 수 있다.

집계할 때 이 둘을 따로 세면 사이드바에 같은 태그가 두 번 보이고, 한쪽을 클릭했을 때 나머지가 강조되지 않아 "왜 이 노트는 빠지지?"가 된다.

**Decision**
집계와 강조 판정 모두 **`normalizeTag` 후 소문자 비교**를 기준으로 한다. 화면에 쓰는 **표기 태그**는 전체 노트를 순회하며 **먼저 등장한 표기**를 채택한다.

**Alternatives**

- **저장된 문자 그대로 따로 집계** — 거부. 구현은 가장 단순하지만 사용자 눈에는 같은 태그가 둘로 보이고, 클릭 결과가 직관과 어긋난다. 기존 중복 검증 규칙과도 기준이 달라져 "어디서는 같고 어디서는 다른" 태그가 된다.
- **가장 많이 쓰인 표기를 대표로** — 거부. "먼저 등장한 것"보다 그럴듯해 보이지만, 노트 하나를 수정하는 것만으로 사이드바 글자가 바뀌어 사용자가 이유를 알 수 없다. 동점 처리 규칙도 추가로 필요하다.

**Consequences**

- (+) 태그 동일성 기준이 앱 전체에서 하나로 통일된다(도메인 계층이 그 기준의 단일 소스).
- (+) 정렬 순서가 안정적이다 — 카운트 내림차순, 동점이면 표기 기준 가나다순.
- (−) 사용자가 `React`로 저장한 노트가 사이드바에 `react`로 보일 수 있다(다른 노트가 먼저 등장한 경우). 표기가 저장값과 다를 수 있음을 감수한다.
- (−) 집계가 순회 순서에 의존하므로, `notes` 순서가 바뀌면 표기가 바뀔 수 있다. 현재 `notes`는 서버 응답 순서 + 생성 순 추가라 안정적이다.

### 강조의 시각적 표현

구체적인 표현(배경·굵기·불투명도)은 **구현 단계에서 `design-system` 스킬로 `docs/design-system/` 정본을 확인해 정한다.** 이 PRD는 제약만 남긴다:

- `NoteItem`은 이미 `isSelected`(지금 편집 중인 노트) 강조를 갖고 있다. **둘은 동시에 나타날 수 있으므로 서로 구분돼야 한다.**
- 선택된 태그 칩도 선택되지 않은 칩과 구분돼야 한다.
- No-Line Rule 등 정본 규격을 따른다. 테두리 추가로 구분하려 하지 않는다.

## 4. Out of Scope

이번 범위에서 **하지 않는 것**을 못 박는다. 아래 항목이 필요해 보여도 구현하지 않고, 별도 기능으로 다시 기획한다.

**필터 동작**

- 노트를 **숨기는** 필터 (강조만 한다 — ADR-2)
- 태그 **다중 선택** (AND/OR 조합)
- 강조된 노트를 **위로 정렬**하기
- 태그 이름으로 **검색**(문자 입력)하기
- "3개 강조됨" 같은 **강조 개수 표시** (노트 개수는 전체 그대로)

**태그 목록 UI**

- 정렬 기준을 사용자가 **바꾸는 UI** (카운트 내림차순 고정)
- 태그가 많을 때 **접기/펼치기**나 스크롤 영역 분리
- 태그 **색상 지정·커스터마이징**
- 태그 목록에서 **태그 이름 변경·전체 삭제**

**상태·저장**

- 선택 태그의 **URL 반영**(`?tag=회의`)이나 링크 공유
- 선택 태그의 **localStorage 저장** (새로고침하면 해제된다)
- 서버에 **필터 관련 데이터 저장** (API·스키마 변경 없음)

**기타**

- 편집기에서 태그를 클릭했을 때의 동작 (사이드바 칩만 클릭 대상)
- 태그 **자동 추천**·연관 태그
- 노트 목록 **가상 스크롤** 등 대량 데이터 대응

## 5. 용어 정의

[`spec-fixed.md` §1](spec-fixed.md)과 동일하다. 요약하면:

| 용어        | 정의                                                         |
| ----------- | ------------------------------------------------------------ |
| 태그 목록   | 사이드바 상단에 표시되는, 전체 노트에서 수집한 태그 집합     |
| 태그 카운트 | 한 태그를 가진 노트의 개수                                   |
| 선택 태그   | 지금 필터로 선택된 태그. 없을 수 있다(전체 보기)             |
| 강조        | 선택 태그를 가진 노트 카드의 시각적 구분. 숨김·정렬이 아니다 |
| 전체 보기   | 선택 태그가 없는 기본 상태                                   |
