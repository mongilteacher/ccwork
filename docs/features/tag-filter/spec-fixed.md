# 태그 필터링 — 확정 요구사항

> `spec-original.md`의 아이디어를 인터뷰로 확정한 문서. 구현·테스트는 이 문서를 기준으로 한다.
> 결정의 **이유(ADR)**는 다음 단계인 `prd.md`에 남긴다.

## 1. 용어 정의 (Ubiquitous Language)

코드·문서·대화에서 아래 단어만 쓴다. 같은 것을 다른 이름으로 부르지 않는다.

| 용어            | 정의                                                                        | 코드 표기                     |
| --------------- | --------------------------------------------------------------------------- | ----------------------------- |
| **태그 목록**   | 사이드바 상단에 표시되는, 전체 노트에서 수집한 태그들의 집합                | `TagFilterBar` 컴포넌트       |
| **태그 카운트** | 한 태그를 가진 노트의 개수. 태그 칩에 함께 표시된다                         | `TagCount { tag, count }`     |
| **선택 태그**   | 지금 필터로 선택된 태그. 없을 수도 있다(전체 보기)                          | `selectedTag: string \| null` |
| **강조**        | 선택 태그를 가진 노트 카드에 주는 시각적 구분. **숨기거나 정렬하지 않는다** | `isHighlighted` prop          |
| **전체 보기**   | 선택 태그가 없는 기본 상태. 아무 노트도 강조되지 않는다                     | `selectedTag === null`        |
| **표기 태그**   | 대소문자가 다른 같은 태그를 하나로 묶을 때 화면에 쓰는 대표 문자열          | `TagCount.tag`                |

- 기존 태그 기능(`docs/features/tag/`)의 용어 **태그·칩·정규화**는 그대로 승계한다.
- "필터"라는 말은 쓰되, 이 기능에서 필터의 의미는 **강조**다. 목록에서 제외하는 동작이 아니다.

## 2. Primary User

**노트가 10~30개 쌓여 태그로 분류해 둔 사용자.** 특정 주제의 노트가 어디 있는지 목록을 훑어 찾는 대신, 태그를 눌러 눈에 띄게 만들고 싶어 한다.

전체 노트를 한 화면에서 계속 보면서(맥락 유지) 관심 있는 것만 도드라지게 하는 것이 목적이다. 그래서 숨기지 않는다.

## 3. 최소 동작 시나리오

1. **태그를 눌러 강조한다** — 사이드바 상단의 `#회의 3`을 클릭 → `#회의`를 가진 노트 3개가 강조되고, 나머지 노트도 목록에 그대로 남는다.
2. **다른 태그로 갈아탄다** — 이어서 `#책 1`을 클릭 → `#회의` 선택이 풀리고 `#책` 노트만 강조된다.
3. **전체 보기로 돌아온다** — 선택된 `#책`을 다시 클릭 → 선택이 해제되고 강조가 모두 사라진다.

## 4. 확정 사항

### 4.1 필터 동작

| 항목           | 결정                                                                |
| -------------- | ------------------------------------------------------------------- |
| 필터의 의미    | **강조만.** 비대상 노트를 숨기지도, 순서를 바꾸지도 않는다          |
| 동시 선택      | **한 번에 하나.** 다른 태그 클릭 시 이전 선택은 자동 해제           |
| 해제 방법      | 선택된 태그를 **다시 클릭**                                         |
| 노트 개수 표시 | `NoteList`의 "노트 N개"는 **전체 개수 그대로** (강조는 개수와 무관) |

### 4.2 태그 목록

| 항목        | 결정                                                                         |
| ----------- | ---------------------------------------------------------------------------- |
| 출처        | 현재 `notes` 전체를 순회해 수집. **서버 요청 없음**                          |
| 위치        | 사이드바(`w-72`) 상단, 노트 목록 위. 레이아웃 단 수는 그대로 2단             |
| 정렬        | **카운트 내림차순**, 동점이면 가나다순(`localeCompare`)                      |
| 카운트 표시 | 칩에 함께 표시 (`#회의 3`)                                                   |
| 대소문자    | **하나로 묶는다.** `React`/`react` → 한 칩. 표기는 **먼저 등장한 쪽**을 따름 |
| 빈 상태     | 태그가 0개면 **영역 전체를 렌더하지 않는다** (제목·구분선 포함)              |

### 4.3 상태 유지

- 선택 태그는 **메모리에만** 둔다. 새로고침하면 전체 보기로 돌아간다.
- URL·localStorage에 저장하지 않는다.
- 소유 위치는 `App.tsx`의 로컬 state — 기존 `selectedNoteId` / `isCreating`과 같은 취급.

### 4.4 경계 조건

| 상황                                         | 동작                                                       |
| -------------------------------------------- | ---------------------------------------------------------- |
| 선택 태그를 가진 마지막 노트에서 태그를 지움 | **자동으로 선택 해제** → 전체 보기                         |
| 선택 태그를 가진 마지막 노트를 삭제          | 위와 동일 — 자동 해제                                      |
| 노트가 0개                                   | 태그 영역 숨김 + 기존 "노트가 없습니다" 그대로             |
| 태그를 가진 노트가 하나도 없음               | 태그 영역 숨김                                             |
| 노트 편집 중(저장 전) 태그를 추가            | 태그 목록은 **저장된 노트 기준**이므로 저장 전에는 안 바뀜 |
| 선택 상태에서 새 노트 작성                   | 선택은 유지. 저장 후 그 태그를 가지면 새 노트도 강조됨     |

### 4.5 에러 처리

**이 기능에는 새로운 실패 지점이 없다.** 서버 요청도, 사용자 입력 검증도 없다(클릭뿐). 따라서 인라인 에러 메시지도 `console.error`도 추가하지 않는다.

노트 로딩 실패·빈 목록은 기존 `NoteList`의 3분기(로딩/에러/빈 배열)가 그대로 담당한다. 태그 영역은 **로딩 중과 에러 상태에서 렌더하지 않는다** — 집계할 `notes`가 없기 때문.

### 4.6 기존 UI 패턴 재사용

- 태그 칩의 생김새는 `TagInput`이 이미 쓰는 칩 스타일을 따른다. 단 **×(삭제) 버튼은 없고**, 대신 클릭 가능해야 한다.
- 강조의 시각적 표현은 **`docs/design-system/`의 정본 규격을 따른다.** 구체적 표현(배경/굵기/불투명도)은 PRD 단계에서 `design-system` 스킬로 결정한다.
- 강조는 `NoteItem`이 이미 가진 `isSelected`(선택된 노트)와 **동시에 나타날 수 있으므로 서로 구분돼야 한다.**
- 태그 칩은 `button` 요소로 만든다 — 「알려진 불일치」 5번(`NoteItem`이 div+onClick이라 키보드 접근 불가)을 새 코드에서 반복하지 않는다.

### 4.7 성능

- 노트 수십 개 규모를 전제한다. 태그 집계는 렌더마다 `notes`를 한 번 순회하는 O(전체 태그 수)로 충분하다.
- **`useMemo`를 쓰지 않는다** — 코드베이스가 파생값을 그냥 계산하는 관습(`NoteEditor`의 `notes.find`)을 따른다. 실측 문제가 생기면 그때 도입한다.

### 4.8 향후 확장 여지 (이번에는 하지 않음)

- 다중 태그 선택(AND/OR) — 선택 상태를 `string | null`에서 `Set`으로 넓히면 된다
- 숨김 방식 필터로의 전환 — 강조 판정 함수를 그대로 필터 조건으로 재사용 가능
- 태그 클릭으로 편집기의 태그 입력에 자동 삽입
- 태그 이름 변경·삭제(전체 노트 일괄)

## 5. 이번 범위에서 제외 (Out of Scope 후보)

PRD에서 확정하되, 인터뷰 시점의 합의는 다음과 같다.

- 노트를 **숨기는** 필터
- 태그 **다중 선택**
- 태그 기반 **검색**(문자 입력)
- 태그 **정렬 기준 변경 UI**
- 선택 상태의 **URL·localStorage 저장**
- 태그 **이름 변경·전체 삭제**
- 태그 **색상 지정**
