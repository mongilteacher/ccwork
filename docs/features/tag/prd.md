## 1. 개요

### 1.1 배경

노트가 쌓일수록 제목만으로는 노트를 분류하기 어렵다. 현재 노트는 `title`·`content`·타임스탬프만 가지며, 사용자가 노트에 의미를 붙일 수단이 전혀 없다.

### 1.2 목표

노트에 **태그를 추가·삭제하고, 노트 상세(편집) 화면에서 태그 목록을 확인**할 수 있게 한다. 태그는 이후 필터링·검색 기능의 토대가 되지만, 이번 범위는 **입력과 표시까지**다.

### 1.3 성공 기준

- 사용자가 노트를 열었을 때 저장된 태그가 칩(pill)으로 보인다.
- 태그 추가·삭제가 저장 버튼 한 번으로 노트 본문과 함께 반영된다.
- 한글 입력(IME) 환경에서 태그가 중복 추가되지 않는다.
- 중복·길이 초과·개수 초과가 사용자에게 **화면으로** 안내된다.

### 1.4 비목표

이번 릴리스는 태그를 **소비**하지 않는다. 태그로 노트를 찾거나 묶는 기능은 전부 다음 단계다. (→ [4. Out of Scope](#4-out-of-scope))

## 2. 사용자 스토리

| ID    | 스토리                                                                          | 인수 조건                                                     |
| ----- | ------------------------------------------------------------------------------- | ------------------------------------------------------------- |

| US-4  | 새 노트를 만들면서 태그를 함께 넣을 수 있다                                     | 생성 시점에 `tags`가 함께 저장된다                            |

## 3. 기술 결정 (ADR)

> 채택 아키텍처: **B안 — 도메인 로직 분리**(순수 함수 `src/domain/tag.ts` + 커스텀 훅 `useTagInput` + 표현 전용 `TagInput`).
> ADR-3이 B안의 핵심이며, 나머지 셋은 `spec-fixed.md`의 잠정 결론을 정식화한 것이다.

### ADR-1. 태그 데이터 저장 위치

_주제: `Note` 문서에 `string[]`로 임베드할 것인가, 별도 컬렉션으로 분리할 것인가_

- **Context**

  백엔드는 `db.json`을 읽는 json-server 목 API다. 조인·트랜잭션·참조 무결성이 없고, 관계를 표현하려면 클라이언트가 직접 여러 요청을 조합해야 한다. 현재 데이터 흐름은 `fetchNotes()` 한 번으로 전체 노트를 받아 Context에 담는 단일 소스 구조이며, 이번 범위의 태그 사용처는 **노트 상세 화면 하나뿐**이다(→ [4.1](#41-태그-소비-검색필터탐색)).

- **Decision**

  `Note` 문서에 `tags: string[]`를 **필수 필드로 임베드**한다. 별도 컬렉션·조인 테이블을 두지 않는다.

  ```ts
  // src/types/note.ts
  export interface Note {
    id: string;
    title: string;
    content: string;
    tags: string[]; // ← 추가 (optional 아님)
    createdAt: string;
    updatedAt: string;
  }
  ```

  기존 노트 3건은 `db.json`을 직접 편집해 `"tags": []`를 넣는다. 마이그레이션 코드를 작성하지 않는다.

- **Alternatives**

  | 대안                                               | 기각 사유                                                                                                            |
  | -------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
  | `/tags` 컬렉션 + `/noteTags` 조인 테이블           | 조회가 3회로 늘고 클라이언트에서 수동 조인이 필요하다. 태그 rename·merge는 out of scope라 정규화의 이점을 못 쓴다    |
  | `tags?: string[]` (optional)                       | 사용처마다 `?? []` 방어 코드가 퍼지고, `createNote`에서 `tags` 누락을 컴파일러가 못 잡는다                           |
  | `tags: string` (쉼표 구분 문자열)                  | 쉼표를 포함한 태그(`"React, Vue"`는 하나의 태그)를 표현할 수 없다. 파싱 책임이 모든 사용처로 번진다                  |
  | 런타임 마이그레이션 (`api` 계층에서 `tags` 정규화) | `src/api/notes.ts`는 순수 fetch 래퍼라는 기존 규약이 깨진다. 목 데이터는 우리가 소유하므로 직접 고치는 편이 정직하다 |

- **Consequences**
  - ✅ `api` 계층 **변경 없음**. 입력 타입이 `Omit<Note, 'id' | 'createdAt' | 'updatedAt'>`, 수정이 `Partial<Note>`라 타입 변경만으로 자동 반영된다.
  - ✅ `tags`가 필수라 `createNote` 호출부의 누락을 `tsc`가 잡는다.
  - ✅ 노트 1건 조회 = 태그 조회. 추가 요청이 없다.
  - ⚠️ 전역 태그 목록·태그 rename은 전체 노트 순회가 필요해진다 — 그래서 out of scope로 뺐다([4.1](#41-태그-소비-검색필터탐색), [4.3](#43-태그-관리-전역-편집)). 나중에 필요해지면 파생 집계(`useMemo`)로 먼저 시도하고, 그래도 부족할 때 컬렉션 분리를 재검토한다.
  - ⚠️ 같은 태그 문자열이 노트마다 중복 저장된다. 노트 수십 건 규모의 실습 프로젝트에서는 무시할 수 있는 비용이다.

### ADR-2. 서버 반영 시점

_주제: 칩 추가·삭제를 즉시 PATCH할 것인가, 저장 버튼에 묶을 것인가_

- **Context**

  `NoteEditor`는 편집·생성 겸용 폼이고, `title`·`content`는 **저장 버튼을 눌러야** 서버에 반영된다. 취소 버튼은 "이 화면에서 한 편집을 전부 버린다"는 의미를 갖는다. 한편 태그는 칩 `×` 클릭처럼 **개별 조작이 즉시 끝나 보이는** UI라, 즉시 저장이 자연스러워 보이는 착시가 있다.

- **Decision**

  칩 추가·삭제는 **로컬 state만 변경**하고, 저장 버튼을 눌렀을 때 `title`·`content`와 **한 번에** 전송한다.

  ```ts
  // 칩 추가/삭제 — 서버 호출 없음
  setTags(next);

  // 저장 버튼 — 1회 요청
  await updateNote(selectedNoteId, { title, content, tags });
  await createNote(title, content, tags);
  ```

- **Alternatives**

  | 대안                                         | 기각 사유                                                                                                                    |
  | -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
  | 즉시 PATCH (칩 조작마다 서버 반영)           | **취소 버튼의 의미가 깨진다.** 태그만 이미 저장돼 취소가 부분 롤백이 된다. `isCreating` 중에는 `id`가 없어 PATCH 대상도 없다 |
  | 즉시 PATCH + 생성 화면만 로컬 버퍼링         | 생성/편집 경로가 이원화돼 테스트 케이스와 버그 표면이 두 배가 된다. 이득(저장을 잊어도 태그가 남음) 대비 비용이 크다         |
  | 디바운스 자동 저장 (N초 후 반영)             | 저장 시점이 사용자에게 보이지 않아 취소 시맨틱이 더 불투명해진다. 본문에도 자동 저장이 없어 일관성이 없다                    |
  | 태그 전용 엔드포인트(`POST /notes/:id/tags`) | json-server가 지원하지 않는다. 지원하더라도 위의 취소 문제는 그대로다                                                        |

- **Consequences**
  - ✅ 취소가 태그 변경까지 자동으로 되돌린다. 별도 롤백 코드가 없다(서버에 안 보냈으므로).
  - ✅ 새 노트 생성과 기존 노트 편집이 **같은 코드 경로**를 탄다.
  - ✅ Context mutation 추가가 불필요하다 — `createNote` 시그니처에 `tags` 파라미터 하나만 붙인다.
  - ✅ 저장 실패 시 태그 로컬 state가 유지돼 재시도할 수 있다(US-10).
  - ⚠️ 태그만 추가하고 저장을 잊으면 유실된다. 이번 범위에서는 감수한다 — 본문 편집도 동일한 성질이라 사용자 기대와 어긋나지 않는다.
  - ⚠️ 입력 필드의 **미확정 텍스트는 버린다**. `Enter`를 누르지 않은 값을 자동 태그화하면 의도치 않은 태그가 생긴다.

### ADR-3. 정규화·검증 책임 계층

_주제: 정규화와 유효성 검사를 `api`·`Context`·UI 컴포넌트 중 어디에 둘 것인가_

- **Context**

  `spec-fixed.md` §5~6은 태그 규칙을 **표로 명세**한다: 4단계 순서 고정 정규화 파이프라인(§5.2), 우선순위 1~4 중 **첫 번째로 걸린 것만** 적용하는 검증(§5.3), 20여 종의 입력 엣지케이스(§6.2). 이들은 React·fetch·DOM과 무관한 **순수 문자열 규칙**이다.

  한편 계층별 역할은 이미 고정돼 있다 — `api`는 순수 fetch 래퍼(ADR-1에서 재확인), `Context`는 상태 + api 오케스트레이션, 컴포넌트는 UI 전용. 그리고 이 프로젝트에는 **테스트 파일이 0개**다(CLAUDE.md 「알려진 불일치」 6번). Testing Library·Vitest는 이미 설치돼 있으나 쓰이지 않는다.

  규칙을 컴포넌트 안에 두면 `normalizeTag` 한 줄을 검증하려고 `render` + `userEvent.type`으로 DOM을 띄워야 한다. 엣지케이스 표 20종 × jsdom 왕복은 느리고, 실패 시 원인이 규칙인지 렌더인지 불분명하다.

- **Decision**

  **규칙 / 동작 / 표현을 3개 파일로 분리**한다.

  ```
  src/domain/tag.ts        순수 규칙 — React·fetch 무의존
  src/hooks/useTagInput.ts 동작 — 입력 state, 에러 메시지, IME 가드
  src/components/TagInput.tsx 표현 — 칩 + input 렌더만
  ```

  ```ts
  // src/domain/tag.ts
  export const MAX_TAG_LENGTH = 20;
  export const MAX_TAG_COUNT = 10;

  export type TagError = 'duplicate' | 'tooLong' | 'tooMany';

  export function normalizeTag(raw: string): string;
  export function validateTag(value: string, tags: string[]): TagError | null;
  export function addTag(tags: string[], raw: string): { tags: string[]; error: TagError | null };
  ```

  - 정규화·검증은 **전부 `domain/tag.ts`**에 둔다. `api`도 `Context`도 태그 규칙을 모른다.
  - `TagInput`은 Context를 소비하지 않고 `{ tags, onChange }` props만 받는다(`NoteItem`과 같은 순수 컴포넌트).
  - 에러는 `TagError` **코드**로 반환하고, 한국어 문구 매핑은 UI 계층이 담당한다.

- **Alternatives**

  | 대안                                     | 기각 사유                                                                                                                            |
  | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
  | A안 — `TagInput` 컴포넌트에 전부 인라인  | 구현은 가장 빠르나 순수 규칙이 컴포넌트에 갇혀 **모든 단위 테스트가 통합 테스트가 된다.** 엣지케이스 20종을 DOM 왕복으로 검증해야 함 |
  | `api/notes.ts`에서 정규화                | "순수 fetch 래퍼" 규약이 깨진다. 검증 실패를 사용자에게 알리려면 에러를 UI까지 역류시켜야 해 흐름이 복잡해진다                       |
  | `NotesContext`에서 검증                  | Context는 서버 데이터의 단일 소스지 폼 검증기가 아니다. 미확정 입력값까지 전역 상태가 알아야 하는 건 과하다                          |
  | 훅 없이 `domain/tag.ts` + 컴포넌트 2계층 | IME 가드·입력 state·에러 클리어 타이밍이 렌더 코드에 섞인다. 분리 비용이 파일 하나라 굳이 아낄 이유가 없다                           |
  | 에러를 한국어 문자열로 반환              | 도메인 계층이 UI 문구를 알게 된다. 문구 변경이 규칙 테스트를 깨뜨린다                                                                |

- **Consequences**
  - ✅ `spec-fixed.md` §5.2·§6.2의 **표를 `it.each`로 그대로 옮길 수 있다.** jsdom 불필요, 밀리초 단위 실행.
  - ✅ 이 프로젝트의 **첫 단위 테스트**가 생긴다. 「알려진 불일치」 6번의 첫 해소 사례.
  - ✅ `TagInput`은 props만 받아 Provider 없이 렌더 테스트할 수 있다.
  - ✅ 규칙 변경(길이 상한, 중복 판정 기준)이 한 파일에서 끝난다.
  - ⚠️ `src/domain/`·`src/hooks/` **두 디렉터리가 새로 생긴다.** 현재 구조는 `api`/`context`/`components`/`types` 4개뿐이다. 이후 기능도 같은 규칙(순수 규칙은 `domain`, 재사용 동작은 `hooks`)을 따르도록 CLAUDE.md에 반영해야 한다.
  - ⚠️ 파일 4개(신규 3 + 테스트 1)로 늘어 108줄짜리 컴포넌트 하나뿐인 코드베이스 기준으로는 무겁게 느껴질 수 있다. 규칙이 명세서에 표로 존재한다는 점이 이 비용을 정당화한다.
  - ⚠️ `npm test`를 pre-commit 훅에 넣을 수 있게 되지만, 넣는다면 `vitest run --passWithNoTests`를 써야 한다(CLAUDE.md 「커밋 규칙」 주의사항).

### ADR-4. 검증 실패의 사용자 노출 방식

_주제: 인라인 메시지를 새 패턴으로 도입할 것인가, 기존 `console.error` 규약을 유지할 것인가_

- **Context**

  현재 이 앱에서 **실패는 사용자에게 전혀 보이지 않는다.** `alert()`을 걷어내면서 저장·삭제 실패도, "제목이 비었음" 검사도 `console.error`만 남았다(CLAUDE.md 「알려진 불일치」 1번). 화면에 에러를 렌더하는 곳은 `NoteList`의 초기 로드 실패 한 곳뿐이다.

  그런데 태그 검증 실패는 성격이 다르다. **사용자가 방금 한 행동에 대한 즉각적 피드백**이며, 아무 반응이 없으면 "Enter가 안 먹었나?"로 읽힌다. 중복·길이 초과·개수 초과는 모두 사용자가 고칠 수 있는 상태라 이유를 알려주는 것이 곧 해결책이다.

- **Decision**

  **입력 필드 바로 아래 인라인 텍스트 한 줄**로 표시한다.

  ```
  ┌───────────────────────┐
  │ react                 │
  └───────────────────────┘
  이미 추가된 태그입니다        ← text-destructive text-xs
  ```

  | `TagError`  | 문구                                      |
  | ----------- | ----------------------------------------- |
  | (빈 값)     | 없음 — 조용히 무시                        |
  | `tooLong`   | `태그는 20자까지 입력할 수 있습니다`      |
  | `tooMany`   | `태그는 최대 10개까지 추가할 수 있습니다` |
  | `duplicate` | `이미 추가된 태그입니다`                  |
  - `alert()`·`confirm()`은 쓰지 않는다(기존 규약 유지).
  - **소멸 시점**: 사용자가 입력값을 바꾸는 순간(`onChange`). 타이머로 자동 제거하지 않는다.
  - 문구 매핑은 UI 계층에 둔다(ADR-3 — 도메인은 코드만 반환).
  - 태그가 10개일 때는 메시지에 더해 **입력 필드를 `disabled`** 하고 placeholder를 `태그는 최대 10개입니다`로 바꾼다.

- **Alternatives**

  | 대안                          | 기각 사유                                                                                                         |
  | ----------------------------- | ----------------------------------------------------------------------------------------------------------------- |
  | `console.error`만 (현행 유지) | 사용자에게 아무 일도 안 일어난 것처럼 보인다. 즉각 피드백이 필요한 상황에 부적합                                  |
  | `alert()`                     | CLAUDE.md 「에러 처리 패턴」이 명시적으로 금지. 흐름을 끊고 연속 입력을 방해한다                                  |
  | 토스트 알림                   | 토스트 인프라(포털·큐·타이머)가 없어 이번 범위 대비 과하다. 입력 필드에서 시선이 멀어져 원인-결과 연결도 약해진다 |
  | 3초 후 자동 사라짐            | 시간이 지나 사라지면 사용자가 원인을 놓친다. 입력값 변경으로 지우는 편이 인과가 분명하다                          |
  | 중복 시 기존 칩을 하이라이트  | 왜 추가가 안 됐는지 설명하지 못한다. 인라인 메시지의 보완재는 될 수 있으나 대체재는 아니다                        |
  | 조용히 무시 (모든 케이스)     | 빈 값에는 적절하나 중복·초과에는 부적절하다. 사용자가 같은 시도를 반복하게 된다                                   |

- **Consequences**
  - ✅ 「알려진 불일치」 1번("실패가 사용자에게 안 보인다")의 **첫 개선 사례**가 된다. 이후 저장 실패·제목 누락에도 같은 패턴을 확장할 수 있다.
  - ✅ 인프라 추가 없이 `text-destructive text-xs` 한 줄로 끝난다.
  - ✅ 에러 코드와 문구가 분리돼 문구 변경이 도메인 테스트에 영향을 주지 않는다.
  - ⚠️ **프로젝트에 새로 도입되는 패턴**이다. 폼 검증 피드백의 사실상 표준이 되므로, 다른 폼에도 같은 방식을 쓰도록 CLAUDE.md에 기록해야 한다.
  - ⚠️ 메시지가 나타나면서 아래 버튼 영역이 밀린다. 영역 높이를 고정하거나 레이아웃 이동을 감수할지 구현 시 결정한다.
  - ⚠️ 스크린리더 사용자에게는 인라인 텍스트 변경이 자동 전달되지 않는다. 라이브 리전은 이번 범위 밖이다([4.7](#47-접근성품질-인지하되-이번엔-다루지-않음)).

## 4. Out of Scope

이번 범위에서 **하지 않는 것**을 명시한다. 아래 항목이 나오면 별도 기능 정의서를 새로 쓴다.

### 4.1 태그 소비 (검색·필터·탐색)

| 제외 항목                             | 이유                                                                                  |
| ------------------------------------- | ------------------------------------------------------------------------------------- |
| 태그로 노트 필터링                    | 목록 상태(선택된 태그)와 필터 UI가 새로 필요하다. 입력이 먼저 안정화돼야 한다         |
| 태그 기반 검색 / 검색어 결합          | 검색 기능 자체가 아직 없다                                                            |
| 사이드바 태그 클라우드·전체 태그 목록 | 모든 노트를 순회해 태그를 집계하는 파생 상태가 필요하고, 정렬·빈도 기준을 정해야 한다 |
| 태그별 노트 개수 표시                 | 위와 동일한 집계 로직에 의존한다                                                      |
| 태그 클릭 시 관련 노트로 이동         | 라우팅이 없다 (현재 단일 화면 + 로컬 선택 상태)                                       |

### 4.2 태그 입력 편의 기능

| 제외 항목                           | 이유                                                                      |
| ----------------------------------- | ------------------------------------------------------------------------- |
| 자동완성 / 기존 태그 추천           | 전체 태그 목록 집계가 선행돼야 한다                                       |
| 쉼표·스페이스로 태그 자동 분리      | `"React, Vue"`는 의도적으로 **하나의 태그**로 둔다 (`spec-fixed.md` §6.2) |
| `Backspace`로 마지막 칩 삭제        | 오삭제 위험이 있고 삭제는 `×`로 충분하다                                  |
| 드래그로 태그 순서 변경             | 순서는 "추가한 순서 유지"로 고정한다                                      |
| 붙여넣기 시 여러 태그 일괄 등록     | 개행은 공백으로 치환해 한 줄 태그로 만든다                                |
| 태그 입력 히스토리 / 최근 사용 태그 | 별도 저장소가 필요하다                                                    |

### 4.3 태그 관리 (전역 편집)

| 제외 항목                   | 이유                                                          |
| --------------------------- | ------------------------------------------------------------- |
| 태그 이름 일괄 변경(rename) | 모든 노트를 순회 갱신해야 한다. 트랜잭션 개념이 없는 목 API다 |
| 태그 병합(merge)            | 위와 동일                                                     |
| 사용되지 않는 태그 정리     | 태그가 노트 문서에 임베드되어 "고아 태그" 개념이 없다         |
| 태그 관리 전용 화면         | 관리 대상 자체가 없다                                         |

### 4.4 태그 표현·메타데이터

| 제외 항목                    | 이유                                                                        |
| ---------------------------- | --------------------------------------------------------------------------- |
| 태그별 색상 지정             | 색상 저장 필드와 팔레트 규격이 필요하다. 칩은 단일 시맨틱 토큰으로 통일한다 |
| 태그 아이콘·이모지 전용 슬롯 | 이모지는 태그 문자열에 포함해 쓸 수 있으므로 별도 필드가 불필요하다         |
| 계층형 태그 (`부모/자식`)    | `/`는 일반 문자로 취급한다                                                  |
| 태그 설명·메모               | 문자열 배열 구조를 벗어난다                                                 |
| 즐겨찾기·핀 고정 태그        | 전역 태그 개념이 없다                                                       |

### 4.5 노출 위치

| 제외 항목                              | 이유                                                                 |
| -------------------------------------- | -------------------------------------------------------------------- |
| 노트 목록 카드(`NoteItem`)에 태그 표시 | 원본 정의서가 "상세 화면에서 확인"만 요구했고, 카드 밀도가 이미 높다 |
| 읽기 전용 상세 뷰                      | 현재 상세 화면이 곧 편집 화면이다 (별도 뷰 모드가 없다)              |
| 태그 개수 뱃지 / 요약 표시             | 위와 동일                                                            |

### 4.6 데이터·인프라

| 제외 항목                         | 이유                                                          |
| --------------------------------- | ------------------------------------------------------------- |
| 기존 데이터 마이그레이션 스크립트 | 목 데이터 3건이라 `db.json`을 직접 수정한다                   |
| 서버 측 유효성 검증               | json-server 목 API에는 검증 훅이 없다. 검증은 클라이언트 책임 |
| 태그 전용 API 엔드포인트          | `Note` PATCH로 충분하다                                       |
| 동시 편집 충돌 처리 / 낙관적 잠금 | 단일 사용자 로컬 실습 환경이다                                |
| 태그 관련 통계·분석               | 제품 범위 밖                                                  |

### 4.7 접근성·품질 (인지하되 이번엔 다루지 않음)

| 제외 항목                                | 비고                                          |
| ---------------------------------------- | --------------------------------------------- |
| 칩 목록의 키보드 내비게이션(방향키 이동) | 입력 필드 + `Enter` + `×` 클릭까지만 보장한다 |
| 스크린리더용 라이브 리전 안내            | 인라인 텍스트 메시지로 대체                   |
| 태그 100개 이상 렌더 성능 최적화         | 상한이 10개라 문제되지 않는다                 |
| `NoteItem` 카드의 기존 접근성 문제 수정  | CLAUDE.md 「알려진 불일치」 5번 — 별도 작업   |

## 5. 용어 정의

| 용어                    | 정의                                                                                                             |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------- |
| **태그(tag)**           | 노트에 붙이는 짧은 문자열 라벨. `Note.tags` 배열의 한 원소                                                       |
| **칩(chip / pill)**     | 확정된 태그 하나를 화면에 표시하는 UI 요소. 라벨 + 삭제용 `×` 버튼으로 구성                                      |
| **확정(commit)**        | 입력 필드의 텍스트가 검증을 통과해 `tags` 배열에 들어가는 순간. `Enter` 키로 발생                                |
| **미확정 텍스트**       | 입력 필드에 남아 있으나 아직 `Enter`로 확정되지 않은 문자열. 저장 시 **버려진다**                                |
| **정규화(normalize)**   | 개행·탭 → 공백 → 연속 공백 축약 → `trim` → NFC 순서로 입력값을 다듬는 과정. 검증·저장은 항상 정규화 값 기준      |
| **NFC / NFD**           | 유니코드 정규화 형식. macOS에서 복사한 한글은 자모 분리형(NFD)일 수 있어 NFC로 통일해야 중복 판정이 정확해진다   |
| **IME 조합**            | 한글·일본어 등에서 글자를 만드는 중간 상태. 이때의 `Enter`는 조합 확정용이며 태그 추가로 이어지면 안 된다        |
| **중복(duplicate)**     | 정규화 후 **대소문자를 무시**했을 때 이미 `tags`에 존재하는 값. 저장값은 먼저 입력된 원문을 유지한다             |
| **인라인 안내 메시지**  | 입력 필드 바로 아래에 한 줄로 뜨는 검증 실패 안내. `alert()`을 쓰지 않는다. 입력값이 바뀌면 사라진다             |
| **`MAX_TAG_LENGTH`**    | 태그 1개의 최대 길이. 20자. `[...value].length`(코드 포인트) 기준                                                |
| **`MAX_TAG_COUNT`**     | 노트 1개의 최대 태그 수. 10개                                                                                    |
| **도메인 계층**         | `src/domain/tag.ts`. React·fetch·DOM을 모르는 순수 규칙 모듈. 정규화·검증이 전부 여기 있다 (ADR-3)               |
| **`TagError`**          | 도메인 계층이 반환하는 검증 실패 코드(`'duplicate' \| 'tooLong' \| 'tooMany'`). 한국어 문구 매핑은 UI가 담당한다 |
| **`useTagInput`**       | 입력 문자열·에러 코드·IME 가드·핸들러를 묶은 커스텀 훅. 확정된 `tags` 배열만 상위로 올려보낸다                   |
| **`TagInput`**          | 칩 목록 + 입력 필드를 그리는 표현 전용 컴포넌트. Context를 쓰지 않고 `tags`/`onChange` props만 받는다            |
| **저장 버튼 반영 방식** | 태그 변경을 로컬 state에만 두고, 저장 버튼을 눌렀을 때 `title`·`content`와 함께 한 번에 서버로 보내는 방식       |
